# إصلاح مطابقة حالات التذاكر — 26 أكتوبر 2026

## النتيجة

أُصلح الاعتماد على أرقام حالات ثابتة. نجحت **27 حالة اختبار آلية** دون فشل، ونجح اختبار النسخة المصححة على Oracle الفعلية بحساب الشركة 1122. البناء نجح دون أخطاء.

تم اختبار نسخة منفصلة على `http://127.0.0.1:5187` ثم إيقافها. الخدمة الأصلية على 5160 لم تُستبدل، وتحتاج إعادة بناء/تشغيل لتفعيل المصدر الجديد. لا يحتاج هذا الإصلاح تغيير جداول أو إعادة ترقيم الحالات أو تشغيل SQL script.

## التغيير

- TicketWorkflow يعرّف الانتقالات والحالات النهائية وحالة SLA عبر StatusCode وIsFinalStatus.
- إنشاء التذكرة يبحث عن OPEN، والإسناد الأول يبحث عن IN_PROGRESS؛ لا يفترضان رقمًا.
- RESOLVED يضبط ActualResolutionDate، والعودة منها للعمل تمسحه، والانتقال منها إلى CLOSED يحتفظ به.
- CLOSED وCANCELLED وكل حالة معلّمة نهائية تمنع إعادة الفتح والتعديل والإسناد والردود والمرفقات.
- تصنيف SLA والتقارير واستعلامات التذاكر المتأخرة والتصعيد تعتمد على المعنى الفعلي للحالة؛ لا تُعامل RESOLVED رقم 3 كأنها Pending Customer.
- أضيف `GET /api/ticket-statuses` ليعيد الحالات المتاحة وأكوادها وأرقامها الحالية. شاشتا التذاكر تحملان هذه الخيارات بدل تخمين الأرقام.
- أضيف اختبار لدورة HTTP بالترقيم الفعلي 1/2/3/4، واختبار مماثل بترقيم 91/207/700/8، واختبارات إضافية للترقيم السابق والحالات النهائية المخصصة.

## ملاحظة تشغيلية عن التهيئة

التشغيل المعتاد للتطبيق يحتوي أصلًا على تهيئة DEV_TEMPLATE ومزامنة API endpoints عند الإقلاع. أول محاولة تشغيل نسخة التحقق مرت بهذا المسار الموجود، ثم أُوقفت. أضيف خياران افتراضيهما true للحفاظ على سلوك التشغيل المعتاد، وشُغلت نسخة الاختبار النهائية وهما false:

```text
Startup__ProvisionDeveloperSchema=false
Startup__SyncApiEndpoints=false
Notifications__Enabled=false
SlaEscalation__BackgroundService__Enabled=false
```

هذه إعدادات نسخة التحقق وحدها، ولا تُحفظ لتعطيل إشعارات النشر أو خدمة المستخدم الحالية.
