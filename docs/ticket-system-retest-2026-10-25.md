# إصلاح نظام التذاكر وإعادة الاختبار

> الحالة الأحدث: أُصلح اختلاف ترقيم الحالات ونجح الاختبار الحي. راجع [إصلاح أكواد الحالات](ticket-status-code-fix-2026-10-26.md).

> تحديث من الاختبار الحي: ترقيم حالات Oracle الفعلية يختلف عن افتراضات الكود؛ تاريخ الحل ومنع إعادة فتح المغلق فشلا عمليًا. راجع [تقرير الشركة 1122](ticket-live-test-company-1122-2026-10-26.md). نجاح الاختبارات المعزولة أدناه لا يعني اعتماد دورة الحالات في بيئة النشر.

بدأ العمل: 25 أكتوبر 2026. آخر تحقق: 26 أكتوبر 2026 بتوقيت عمّان.

## السياسة المطبقة

- المستخدم العادي ينشئ تذكرة باسمه وشركته وفرعه الموثوق، ويقرأ ويعدل تذاكره ويضيف الردود العامة والمرفقات إليها.
- أدمن الشركة يقرأ ويدير تذاكر شركته، بما يشمل فروعها، دون الوصول لشركة أخرى.
- السوبر أدمن يدير تذاكر الشركة المختارة عبر X-Company-Id أو X-Company-Code. عليه اختيار شركة أولًا؛ لا تُستخدم هويته كسجل صاحب طلب في SYS_USERS.
- التذكرة الجديدة تظهر بصندوق أدمن شركتها وصندوق السوبر أدمن عند اختيار تلك الشركة. الإسناد اختياري ومنفصل عن وصولها للصندوق.
- الإشعارات العامة تُوجَّه لصاحب الطلب والمسؤول المعيّن وأدمن الشركة الفعالين والسوبر أدمن الفعالين، مع إزالة تكرار البريد. لا يُخطر أدمن شركة أخرى.
- تغيير الحالة والإسناد والحذف والتقارير للمخولين بالإدارة فقط. الملاحظات الداخلية يكتبها ويقرؤها المخولون فقط.

## ما تم إصلاحه

| المشكلة | الإصلاح |
|---|---|
| عزل الشركات والملكية | TicketAccessFilter يراجع المستخدم الفعلي، ويفعّل QueryFilters على التذاكر والتعليقات والمرفقات في OracleDbContext. لا يعتمد الوصول على مخطط الجلسة وحده. |
| هوية صاحب الطلب | إنشاء التذكرة يستبدل سياق العميل بالسياق الموثوق؛ يتحقق من نشاط الفرع وتبعيته للشركة وعضوية المستخدم فيه. |
| صلاحيات قديمة في الرمز | تُراجع IsAdmin وIsActive من الحساب الحالي، وتُراجع عضوية الفرع عند الإنشاء. |
| وصول الأدمن والسوبر أدمن | اختيار مستلمين صريح من الحسابات الفعالة مع تقييد أدمن الشركة وإزالة تكرار البريد. |
| شاشة السوبر أدمن | تمرير X-Company-Id من محدد الشركة لكل طلب، وإصلاح قيم تجميع التقرير. |
| شاشة المستخدم | تعطيل تغيير الحالة والملاحظة الداخلية لغير الأدمن؛ يبقى المنع الحقيقي في الخادم. |
| الحذف | DeleteTicketCommand مستقل ينفذ soft delete، مع استبعاد المحذوف من الجلب المباشر والقوائم والمرفقات. |
| حفظ الحالة والإسناد | UpdateAsync يحفظ AssigneeId وTicketStatusId وتواريخ المهلة والحل صراحة، بدل الاعتماد على تتبع كائن سابق. |
| مهلة الحل | حفظ الأولوية السابقة قبل المقارنة وإعادة حساب المهلة عند تغييرها. الوقت UTC وساعات متصلة. |
| التقارير | تنفيذ الحجم والالتزام والعبء والاتجاهات على بيانات فعلية بدل إرجاع new() دائمًا. |
| البحث | تنفيذ الحالات والأولويات والأنواع والتصنيفات وSLA والمدى الزمني وAND/OR؛ نطاق الشركة والملكية يبقى إلزاميًا خارج OR. ترتيب من قائمة مسموحة مع كسر التعادل برقم التذكرة. |
| المرفقات عند الإنشاء | فحص جميع المرفقات قبل الحفظ، ثم حفظ التذكرة ومرفقاتها كشبكة كيانات في SaveChanges واحد. EF relational يستخدم transaction لهذه العملية. |
| التعليقات الداخلية | إظهارها للمخولين فقط، منع إنشائها من المستخدم العادي، ومنع إرسال محتواها كإشعار عام. |
| إشعارات البريد | طابور محفوظ على القرص، محاولات مع تراجع زمني، حالة فشل/تعليق/إرسال، واستمرار الرسائل بعد إعادة التشغيل. نجاح API لا يُعرض كدليل تسليم بريد. |
| التصعيد | استبعاد الحالات النهائية، استعمال UTC، وتمييز تنبيه قرب الموعد عن تجاوزه. بصمة الرسالة تمنع تكرار التنبيه نفسه في كل دورة. |

أضيف TicketSupportDirectory ليقرأ أدمن الشركة من مخطط الشركة المسجل في السجل المركزي حتى عند تشغيل التصعيد من خلفية تعمل في مخطط الماستر، دون تغيير جلسة الطلب. اسم المخطط يُتحقق منه، ومعرف الشركة يُمرر كمعامل SQL.

توضيح على التقرير الأول: حقول CompanyId وBranchId وRequesterId في CreateTicketCommand عليها JsonIgnore أصلًا؛ لذلك اختبار الاستدعاء المباشر القديم لم يكن إثباتًا لإمكانية تزوير هذه الحقول عبر JSON. تمت إضافة فرض للسياق الموثوق وفحص عضوية الفرع كدفاع إضافي، واختبار HTTP يؤكد تجاهل القيم المخالفة المرسلة.

## الاختبارات

**نتيجة مجموعة التذاكر: 21 ناجح، 0 فاشل، 0 متجاوز.** ملف النتائج `output/ticket-audit/ticket-fixed-verified.trx`. الفحص الرجعي للمخزون نجح أيضًا: **75 ناجح، 0 فاشل**، بنتائج `output/ticket-audit/ticket-inventory-regression.trx`. أُجري فحص المخزون بعد مرشحات DbContext وقبل إضافة دليل مستلمي الدعم المستقل، وهو لا يغير مرشحات المخزون. بناء API الأخير نجح دون أخطاء، مع تحذيرات بالمشروع. فحص صياغة JavaScript لشاشتي التذاكر نجح باستخدام `node --check`؛ لم تُجرَ معاينة تفاعلية للشاشتين.

المشروع `tests/ThinkOnErp.TicketAudit.Tests` ضمن الحل، ويجمع اختبارات وحدة واختبارات HTTP باستخدام TestServer مع ملفات Controller وFilter الأصلية، وHandlers وRepositories وخرائط EF الأصلية.

تغطي الاختبارات:

- إنشاء التذكرة بسياق المستخدم وتجاهل الشركة/الفرع/صاحب الطلب المزيفين في JSON.
- ظهورها لأدمن شركتها والسوبر أدمن في النطاق المحدد.
- منع مستخدم آخر وشركة أخرى من قراءتها أو تنزيل مرفقها، ومنع القائمة لشركة مخالفة.
- إسنادها لأدمن شركتها ورفض إسنادها لأدمن شركة أخرى.
- الردود الداخلية: الحجب عن المستخدم، والإظهار للأدمن، ورفض الكتابة غير المصرح بها.
- حفظ الحالة والإسناد وتاريخ الحل وإعادة القراءة من سياق قاعدة بيانات جديد لكل طلب.
- الحذف ثم رفض الجلب واختفاؤها من القائمة.
- تغيير الأولوية وتحديث مهلة الحل، وفلاتر AND/OR والتقارير ذات البيانات الفعلية.
- رفض طلب دون مصادقة، ورفض سوبر أدمن دون اختيار شركة.
- رفض تذكرة فارغة عبر Validator وValidationBehavior الأصليين، ومرفق بمحتوى مخالف دون ترك تذكرة جزئية.
- سحب صلاحية الأدمن وإزالة عضوية الفرع بينما الرمز القديم ما زال قائمًا.
- اختيار بريد الأدمن الصحيح والسوبر أدمن الفعال، وإرسال الرسائل للطابور دون إخطار شركة أخرى.
- حفظ رسالة معلقة دون SMTP، واستعادتها بعد إنشاء نسخة خدمة جديدة، ومنع تكرارها.
- فشل SMTP ثم إعادة المحاولة وتسليم الرسالة إلى خادم SMTP محلي للاختبار عبر MailKit الحقيقي.
- توليد SQL باستعمال Oracle provider بإعداد Oracle 19 للجلب مع مرشحات التذاكر والتعليقات والمرفقات، دون الاتصال بقاعدة حقيقية.

استُبدل محلل الشركة المرتبط بـOracle ومصادقة JWT في مضيف HTTP بهوية/شركة اختبار؛ محرك قواعد التحقق الديناميكية الخارجي مستبدل بنتيجة فارغة. الاختبارات لا تدعي اختبار تسجيل الدخول الحقيقي أو قواعد تحقق محفوظة في قاعدة الإنتاج. قاعدة HTTP هي EF InMemory، ولا تثبت قيود Oracle أو rollback على خادم Oracle فعلي.

## تهيئة البريد ومراقبته

إعدادات البيئة المطلوبة للتسليم الخارجي:

```text
Notifications__Enabled=true
Notifications__Smtp__Server=<smtp host>
Notifications__Smtp__Port=587
Notifications__Smtp__Username=<account>
Notifications__Smtp__Password=<secret>
Notifications__FromEmail=<sender address>
Application__BaseUrl=<frontend base URL>
Notifications__QueueDirectory=<persistent private directory>
```

الاتصال الافتراضي STARTTLS؛ يمكن استخدام `Notifications__Smtp__Security=SSL` للمنفذ المناسب. لا يتم تعطيل التحقق من شهادة TLS. الاتصال غير المشفر محصور باختبار localhost مع اختيار صريح.

`GET /api/ticket-delivery/status` متاح للسوبر أدمن ويعيد Configured وPending وFailed وSent. Sent يعني قبول خادم SMTP للرسالة، وليس تأكيد وصولها لصندوق البريد النهائي. Failed جزء من Pending، وقد يشمل ملفات معطوبة معزولة.

إن غابت إعدادات SMTP تبقى الرسائل Pending ويظهر Configured=false. لم أضع بيانات اعتماد وهمية ولم أغيّر أسرار النشر.

الطابور ملفي ومناسب لمضيف واحد؛ مجلده يجب أن يبقى بعد إعادة النشر وتكون صلاحياته خاصة بحساب الخدمة. الرسائل المرسلة تُحفظ لمنع التكرار، وتحتاج سياسة احتفاظ تشغيلية. التسليم at-least-once: تعطل العملية بعد قبول SMTP وقبل تثبيت الحالة قد ينتج تكرارًا. حفظ تذكرة Oracle وكتابة رسالة القرص ليسا transaction واحدة؛ ضمان عدم فقد أي حدث عند الانهيار بين العمليتين يحتاج DB Outbox ضمن ترحيل قاعدة بيانات منفصل. لا يُدّعى توفير هذا الضمان هنا.

## حدود الاعتماد

الإصلاحات ضمن ملفات المصدر، ولم يتم استبدال الخدمة المحلية الجارية أو نشرها على الإنتاج. اختبار SMTP المحلي لا يثبت وصول رسالة لصندوق أدمن/سوبر أدمن حقيقي، ولا يثبت إعدادات البريد الخارجي. يلزم اختبار نشر على Oracle التجريبية وبيانات حسابات فعلية قبل اعتماد بيئة الإنتاج، بما يشمل صلاحيات THINKON_SUPPORT ومراجع مستخدمي الشركات واستعلامات التصعيد الخلفية في سياق النشر.
