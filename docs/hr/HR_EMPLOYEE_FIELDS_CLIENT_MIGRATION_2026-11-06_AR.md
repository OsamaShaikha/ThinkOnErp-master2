# OPS-09 — انتقال عميل API إلى صلاحيات حقول الموظف

6 نوفمبر 2026. تجهيز عقد قابل للمراجعة، وليس إثبات نشر عميل أو قبول واجهته.

GET قائمة/تفاصيل الموظف قد يعيد null للهوية/الميلاد/الخصائص الشخصية والبنك والراتب، وتصبح حقول القيمة الخاصة nullable. fieldVisibility يحدد الحجب وإمكانية التعديل؛ لا تعرض null كميلاد افتراضي أو صفر راتب أو عدم وجود معالين. لا تُرسل نسخة من الرد المحجوب إلى PUT الكامل.

- تعديل الأسماء/العمل/التنظيم يستخدم PUT {code}/work-profile بالحقول المعرفة فقط.
- تعديل البنك يستخدم PUT {code}/bank بثلاثة مفاتيح صريحة؛ null يعني مسحاً مقصوداً. لا يرسل الهوية أو العمل.
- تعديل الهوية يستخدم PUT {code}/identity بمجموعة الهوية الكاملة؛ لا يرسل Bank أو UserId أو حقول العمل.
- PUT الكامل يبقى للعميل الذي يملك edit-identity وedit-bank ويكوّن استبدالاً كاملاً مقصوداً. نقل الفرع يحتاج edit للمجموعات الثلاث في الفرعين.
- لا تجعل edit-bank أو edit-identity إذناً لعرض قيمة محجوبة؛ الرد يتبع حقوق العرض المستقلة. عند كتابة دون عرض، لا تربط null المحجوبة بحفظ تلقائي.
- المعالون يحتاجون edit-identity؛ الإضافة تحتاج view-identity أيضاً. الراتب يحتاج view-salary وكتابتُه edit-salary. لا تستخدم generic create/edit كبديل لهذه الحقوق.
- تصدير الصفوف يحتاج ميزات العرض الثلاث؛ الاستيراد والمعاينة يحتاجان الست، إضافة إلى صلاحية العملية. عرض صف المعاينة ليس إذن تنفيذ ويعاد التحقق عند الحفظ.

قبل نشر هذا العقد على عميل فعلي، يجهز كتالوج الميزات وروابط hr-employees في مخططه، ويحدد مسؤول الشركة المنح عبر النظام الحالي. لا تعيين تلقائي لمستخدم أو دور. عدم تسجيل الشاشة/الميزة أو تعطيلها يرفض الوصول لغير الإداري، ولا يُفترض تطابق DEV_TEMPLATE مع العميل.

اختبارات الواجهة المطلوبة: مستخدم عرض عام يرى العمل بلا بيانات خاصة، كاتب بنك مستقل يحفظ البنك دون مس الهوية، تعديل عمل لا يرسل حقولاً مخفية، رسائل رفض full PUT وExcel مفهومة، وسحب المنح يعكس الحالة في الطلب التالي. هذه الواجهة لم تُختبر أو تُنشر هنا. قبول عميل تجريبي ومخططين عبر Oracle HTTP ضمن OPS-03/05/07/10 وBASE-04.
