# EMP-13 — حماية تغيير ربط حساب الموظف

6 نوفمبر 2026. استكمال جزء التنفيذ في EMP-03 دون تغيير الجداول أو بصمات الرواتب القديمة. بقي مسار PUT /api/hr/employees/{code}/user-link بصلاحية AdminOnly وhr-employees/link-user؛ لا يضيف الربط دوراً أو منحة مدير/فريق.

## التنفيذ

LinkEmployeeUserAsync يتطلب IHrUnitOfWork ولا يرجع لمسار غير محمي. يُطبع رمز الموظف وتتحقق هوية الحساب/محرر العملية قبل الدخول. ExecuteEmployeeAccountAsync يرفض سياق الشركة المفقود والخدمة الذاتية والتغييرات المعلقة، ويعمل داخل ReadCommitted. يقفل مرساة الشركة، ثم كل فترات الشركة مرتبة، ثم صف الموظف، ويعيد فحص الشركة والفرع والمرئية ويعيد تحميل الجذر المتعقب قبل قراءة شروط الربط. هذا الترتيب ينسق مع حراس الملف والاستيراد والفترة دون إعادة فتح فترة مالية.

يُقفل صف حساب الدخول أثناء التحقق داخل معاملة Oracle لمنع تبديل شركته/تفعيله قبل الحفظ. الربط يحتاج موظفاً فعالاً وحساباً فعالاً من الشركة نفسها وله عضوية في فرع الموظف الفعال. تكرار الحساب محمي بتحقق الخدمة والقيد الفريد القائم؛ لا تُرجع بيانات موظف آخر عند الرفض. النطاق المصرح يظل مطلوباً لإلغاء الربط أيضاً؛ الحارس لا يتجاوز شركة/فرعاً غير متاح. إلغاء الرابط يسمح بموظف منتهٍ أو فترة CLOSED ولا يحذف الموظف أو يعيد تنشيط/تعطيل الحساب. دورة إيقاف حساب المنتهي مستقلة؛ لا تُضاف صلاحيات أو رسائل أو منح دائمة.

UpdateEmployeeUserLinkAsync يكتب UserId وUpdateUser وUpdateDate فقط، ويلحق الجذر وحده عند فصله دون تتبع graph. لذلك لا تُعاد كتابة اسم/راتب/معال قديم أثناء الربط. تكرار الرابط نفسه لا يكتب تدقيقاً جديداً. حُصر تعطيل حساب المنتهي أثناء الحفظ في الموظفين المعدلين/الجدد، حتى لا تعطل قراءة موظف منتهٍ آخر حسابه عند حفظ رابط مختلف.

الفشل في المعاملة المملوكة يتراجع وينظف التعقب، بما فيه الإلغاء باستخدام rollback لا يتأثر برمز الإلغاء. المعاملة الخارجية مسؤولية مستدعيها عند الفشل. لا يُثبت استعمال InMemory ذرية Oracle أو أقفاله.

## بصمة الرواتب

لم يتغير تنسيق InputFingerprint أو أي بصمة محفوظة. اللقطة الحالية تشمل الموظف وUserId وحقول التدقيق. لذلك تغيير رابط حقيقي بعد حساب مسير غير معتمد يجعل البصمة مختلفة ويتطلب إعادة حسابه قبل الاعتماد؛ تكرار الرابط نفسه لا يفعل ذلك. قفل الفترات ينسق مع الحساب/الاعتماد، دون رفض تغيير أمني لمجرد CLOSED أو وجود مسير معتمد. لا يعيد العمل حساب المعتمد أو يكتب صافي/سطور رواتبه أو يعدل بصمته التاريخية.

## الأدلة

- emp03-account-hr.log: اختبارات HR المركزة، ومنها الحارس قبل القراءة، انعدام fallback، إعادة فحص الحالة، والحفظ المخصص.
- emp03-account-api.log: عقود/فلتر/HTTP/نطاق؛ مستخدم عادي مرفوض حتى مع ادعاء isAdmin، إداري فعلي يربط ويلغي، شركة أخرى لا تتغير، بيانات قديمة لا تُمس. توجيه HTTP وraw ما زالا adapters ومخزنين InMemory.
- emp03-account-oracle.log: قفل حقيقي، إعادة قراءة جذر تغير عبر SQL داخل fixture، رفض التكرار، الربط المتكرر وبصمته، إلغاء الرابط عند CLOSED ولموظف منتهٍ، ثم rollback والتحقق من استعادة الملف/الرابط/الحالة وغياب الفترة وأي عضوية فرع مؤقتة للاختبار.
- emp03-account-preservation-after.log: مقارنة مستقلة للجداول الأصلية بعد انتهاء fixtures.

## جزء OPS-04: جلستان فعليتان

--verify-employee-account-locks يفتح جلستين: الحارس الأول يحتفظ بأقفاله، وNOWAIT في الثانية يُرفض على مرساة الشركة وصف الموظف؛ الحارس الثاني ينتظر ثم يدخل بعد تحرير الأول. الـcallbacks لا تنفذ DML، ولا تُغير ملفاً أو حساباً أو منحة أو راتباً. هذا يثبت احتجاز القفل والتسلسل لهذا المدخل فقط؛ لا يثبت سباق اعتماد/تعديل مالي كامل أو تزامن المديرين/الإقفال/الاستيراد أو توجيه العملاء.

EMP-03 تبقى مفتوحة لمراجعة صلاحيات المدير/الفريق وفصل EMP-04 الحساس والمصفوفة الكاملة عبر HTTP على Oracle/عميلين. OPS-04 تبقى جزئية لباقي سيناريوهات التزامن.
