**آخر تحديث:** 5 نوفمبر 2026

الغرض من الملف أن يكون سجل اتفاقات وقرارات وخطوات تنفيذ. نحدّث الحالات بعد كل مرحلة ونربط المهام بأدلة الكود والقبول. «موجود» يعني ظهر في المستودع؛ لا يعني أنه منشور أو مجرّب على قاعدة الإنتاج.

## قرارات صاحب النظام

| الموضوع | القرار الحالي | ملاحظات/أثر |
|---|---|---|

| نمط الدوام | الموظف قد يحمل إسنادات شفت متزامنة؛ الإسناد ذو الفترة المحددة يتغلب على الإسناد العام/الأساسي | مثال: شفت أساسي مستمر وشفت رمضان لفترة. نحتاج قاعدة صريحة لمنع/حل تعارض شفتين محددين بالفترة نفسها. |
| الشفت الليلي | لم يحسم | نختار تمثيل يوم العمل بعد تحديد قواعد التقارير والغياب؛ يجب أن يعمل الشفت العابر لمنتصف الليل. |

| نهاية الخدمة | تشمل الاستقالة، انتهاء العقد، الفصل، التقاعد، الوفاة، وترك العمل؛ مع تسوية كل الاستحقاقات والحركات المالية المعلقة والإجازات | يلزم التفريق بين سبب المغادرة، آخر يوم عمل، تاريخ التسوية، وحالة سير العمل. |

| الحضور الذاتي | إذا كان مطلوباً منه الدوام أونلاين ولم يسجل حضوراً: غياب؛ المداوم أونلاين يحتسب حضوره؛ النسيان يعالج كـMissing Punch بطلب وموافقة | يلزم تعريف «مطلوب منه الدوام أونلاين» كصفة جدول/سياسة، لا استنتاجه من عدم وجود بصمة فقط. |
| الإجازات | استحقاق آلي مع تصحيح يدوي مضبوط بالصلاحية؛ الترحيل والتحويل حسب العميل ونوع الإجازة؛ الإجازة السنوية المستحقة هي المرشحة للتحويل النقدي | قواعد الاستحقاق والتقريب، وتوقيت إقفال السنة تحتاج توثيقاً لكل سياسة. |
| سنة الإجازة والإقفال | تاريخ بدء سنة الإجازات يحدده العميل، وقد يكون في أي شهر مثل سبتمبر؛ قواعد الإقفال والترحيل تختلف حسب نوع الإجازة | لكل نوع يمكن إيقاف الترحيل، ترحيل كامل/جزئي بسقف أيام، تصفير/انتهاء الرصيد أو تسوية الزيادة نقدياً. يلزم اعتماد إقفال Posted مع إمكانية Unpost بصلاحية وتدقيق. |
| أنواع الإجازات | إعداد ديناميكي لكل شركة؛ السنوية والمرضية وغير المدفوعة أمثلة، وليست إلزامية | الشركة تحدد الأنواع التي تريدها، بما فيها عدم إعداد إجازة مرضية، وتضيف أنواعاً عند الحاجة. المنتج لا يفرض قواعد حسب البلد. |

| جدول الشفت اليومي | مطلوب | إسناد شفت فعلي لكل موظف/تاريخ، مع استخدام الأساسي والمؤقت كقواعد/قوالب لتوليد الجدول؛ الجدول اليومي الصريح يحسم الاستثناءات. |
| عرض رصيد الإجازات | API يعرض الرصيد المستخدم والمتبقي، مع تفضيل لكل شركة: Decimal أو D/H/M | إعداد العرض تنسيق فقط ولا يغير وحدة التخزين/الاحتساب. |
| تكرار استحقاق الإجازة | حسب إعداد كل شركة/نوع: سنوي أو شهري أو يومي | التشغيل الآلي ومنع تكرار إضافة الاستحقاق أساسيان قبل الاعتماد المالي. |
| الرواتب | النظام يحسب صافي الراتب ويعتمد المسير | يتطلب تثبيت نسخة مدخلات وحسابات المسير، ومسارات فصل الإعداد والحساب والاعتماد والترحيل والدفع. |
| نسخة أولية | البدء بنسخة تأسيسية ثم التوسع | لا تشمل الإضافي أو دورة التسوية النهائية الكاملة حتى يجهز الأساس وتُحسم السياسات. |

## أدلة أولية من المستودع

مصدر الحالة: `docs/HR_MODULE_STATUS_2026-11-02.md`، ومرجع المسارات `docs/HR_API_REFERENCE_2026-11-02.md` و`docs/HR_API_INVENTORY_2026-11-02.json`.

- الجرد المذكور يستخرج 77 نقطة API من 11 متحكماً؛ هذا جرد كود وليس إثبات نشر أو تكامل تشغيلي.
- الموظفون: API الملف والبحث والاستيراد/التصدير والربط الاختياري بحساب النظام موجودة. المدير ممثل حالياً بحقل `ManagerEmployeeCode` في كيان الموظف.
- الأقسام تظهر كـ`DepartmentCode` على الموظف، ولم يظهر في جرد HR متحكم CRUD للإدارات أو بنية شجرة/مدير إدارة. يلزم تتبع جداول ERP المشتركة قبل استنتاج الحاجة لجدول جديد.
- الحضور: API دخول/خروج GPS وحالة اليوم والفروع القريبة، وطلبات تصحيح الحضور موجودة. مسار التصحيح يمكن أن يكون أساس Missing Punch، لكن يجب التأكد من أنه يفرض الحقول والحالة والموافقة المطلوبة.
- `RawAttendance` يدعم المصدر BIOMETRIC وMOBILE_APP ومعرّف خارجي وجهاز. `AttendanceDay` يحتوي حالة اليوم و`HasMissingPunch` و`OvertimeHours`.
- `ShiftSchedule` و`EmployeeShiftAssignment` موجودان كنماذج بيانات، لكن لا تظهر واجهات إدارة/إسناد شفت ضمن الـ77 API. النموذج الحالي لا يبيّن أولوية عند تداخل إسنادات الشفت.
- محرك احتساب الحضور يقرأ سياسة وساعات شفت، ويعيّن Missing Punch؛ وتوجد خدمة حساب إضافي. هذا لا يثبت وجود دورة موافقة إضافي أو اعتماد تشغيلها.
- الإجازات وأنواعها وطلباتها وأرصدتها وسياساتها لها أساس API وخدمة، مع فجوات موثقة في دفتر الحركات وإلغاء الطلب/إرجاع الرصيد ومنع التكرار وإقفال السنة.
- الرواتب والسلف والقروض والتعديلات والمسيرات والترحيل المحاسبي موجودة جزئياً. التقرير يوثق خللاً عالي الأثر: إنشاء تعديل الراتب يضعه معتمداً تلقائياً. كما يوثق أن معاينة ملف البنك محمية بعرض بدلاً من صلاحية التصدير.
- كيان الموظف الحالي يحفظ `TerminationDate` و`TerminationReason` مباشرة، لكن لم يظهر في جرد API مسار مستقل لإجراءات نهاية الخدمة والتسوية النهائية.
- جداول/نماذج موجودة حسب فحص EF السابق: 34 مستخدمة من 59 جدول HR في فحص قاعدة DEV_TEMPLATE بتاريخ 8 أكتوبر. هذه الأرقام قديمة وتحتاج إعادة تحقق قبل قرارات ترحيل.
- الـAPI الحاضرة يجب ألا تُحذف اعتماداً على عدم ظهورها في الواجهة وحدها؛ نتحقق من مستهلكيها (موبايل، ERP، تقارير، تكاملات) أولاً.

## خريطة المجال المستهدفة مبدئياً

```text
العميل/الشركة ضمن عزل ERP الحالي
├── الإعداد التنظيمي: الإدارات، الفروع، المسميات، المديرون
├── الموظف ── حساب المستخدم/الصلاحيات (علاقة اختيارية)
│   ├── تواريخ العمل والراتب والعقد
│   ├── جداول/إسنادات الشفت ذات فترة سريان وأولوية
│   ├── RawAttendance (موبايل/جهاز) → معالجة يومية → تصحيحات/Missing Punch
│   ├── طلب مغادرة قصيرة أثناء الدوام
│   ├── طلبات الإجازة → موافقات → دفتر حركات الرصيد
│   └── مكونات الراتب/السلف/الاقتطاعات → مسير ثابت النسخة → اعتماد
└── إنهاء خدمة → إيقاف/إقفال علاقات العمل → رصيد إجازة وتسوية راتب
    → استحقاقات نهائية → قيود ERP ودفع وفق مسارات الاعتماد
```

هذه خريطة مفاهيمية وليست قراراً بأن كل صندوق يجب أن يكون جدولاً مستقلاً. جميع المفاتيح والعلاقات يجب أن تراعي نمط الشركة/الفرع الحالي في ERP.

## الخطة المرحلية وسجل التنفيذ

### المرحلة 0 — جرد موحد للعقود والبيانات **قيد العمل**

- [x] قراءة تقرير حالة HR وجرد الـAPI الحاليين.
- [ ] تدقيق كيان/جدول/مفتاح/علاقة لكل نطاق HR مقابل قاعدة البيانات الحالية، وتحديد ما هو قديم من تقرير 8 أكتوبر.
- [ ] ربط كل API بمستهلكه الفعلي (واجهة ويب، موبايل، ERP، مهمة خلفية، تكامل خارجي) وحالته، ثم قرار إبقاء/تعديل/إيقاف.
- [ ] تثبيت مصفوفة العزل: Company/Tenant وBranch لكل كيان، ومفاتيح العلاقات، واختبارات منع الربط/القراءة عبر العملاء.
- **المخرج:** مخطط علاقات موثق + سجل API مع المستهلك والحالة والفجوات.

### المرحلة 1 — أساس الموظف والتنظيم والصلاحيات

- مراجعة الموظف، المدير المباشر، الإدارة، الفرع، المسمى، ربط حساب الدخول، وتواريخ السريان.
- الاستفادة من Roles/Permissions الحالية بعد التحقق من تفصيلها. لا ننشئ HR role خاصاً تلقائياً: نحدد هل المطلوب دور إعداد مسبق فقط أم صلاحيات جديدة؛ الموظف والمدير صفتان/علاقتان وظيفيتان وليستا بالضرورة نوع حساب.
- حماية البيانات الحساسة (الراتب، البنك، الهوية) بصلاحيات مستقلة عن عرض ملف الموظف متى سمح نموذج الصلاحيات بذلك.
- **قبول:** لا تسرب عبر المستأجر/الفرع، لا تكرار معرفات الموظف داخل نطاق غير مسموح، وتظهر تبعية المدير بشكل صحيح.

### المرحلة 2 — الدوام والشفتات والحضور الأساسي

- اعتماد قواعد الإسناد: شفت أساسي مفتوح المدة + شفت مؤقت بأولوية أعلى، وتحديد قاعدة التعارض عند وجود إسنادين مؤقتين.
- API وشاشة لإنشاء/تعديل/إلغاء/جدولة/إسناد الشفتات، مع فترة سريان، أيام عمل، استراحة، منطقة زمنية، وشفت عابر منتصف الليل.
- تحديد سجل الدوام المطلوب لكل موظف/يوم حتى نفرّق بين «لا دوام» و«كان يجب أن يداوم ولم يسجل».
- ربط تدفق الموبايل الموجود: أحداث Check-in/Check-out مع الموظف، الوقت والمنطقة الزمنية، الموقع، الفرع، مصدر الحدث، ومعرّف idempotency يمنع التكرار.
- Missing Punch: طلب موظف أو مسؤول مع سبب وأوقات مقترحة، موافقة شخص مخول، حفظ الأثر الأصلي والجديد وإعادة احتساب اليوم.
- **خارج النطاق حالياً:** الموافقات والدفع الفعليان للإضافي؛ نخزّن ساعات الحساب فقط إذا لزم، ولا تدخل الصافي قبل اعتمادها.
- **قبول:** حالات جدول/عطلة/إجازة/غياب/حضور/نقص بصمة صحيحة، تكرار الطلب لا يكرر الحدث، والتصحيح لا يعدّل مسيراً أو فترة مقفلة بصمت.

### المرحلة 3 — الإجازات والأرصدة

- توثيق سياسة كل عميل ونوع: الاستحقاق، تاريخ البداية، الكسور والتقريب، الأهلية، الترحيل والانتهاء، والسقف.
- سجل حركات رصيد غير ملتبس: استحقاق، طلب معتمد، إلغاء/عكس، تعديل يدوي مسبب، ترحيل، تصفية نقدية.
- دعم الصلاحيات والموافقات والإلغاء وإعادة الرصيد، منع تشغيل شهري/سنوي مكرر، وتثبيت أثر الإجازة في الحضور والرواتب.
- التصفية النقدية فقط للأنواع المسموح بها حسب سياسة العميل؛ السنوية المستحقة هي النطاق المقصود مبدئياً.

### المرحلة 4 — الرواتب وربط ERP

- إصلاح واعتماد حالات تعديلات الراتب والسلف والقروض قبل أي اعتماد مالي.
- تعريف مكونات الراتب والضمان والضرائب حسب سياسة العميل/البلد وتاريخ السريان، ومراجعة ضوابط البيانات البنكية والتصدير.
- مسار مسير: إعداد فترة → تحقق مدخلات → حساب/معاينة → مراجعة فروقات → اعتماد → ترحيل ERP → ملف بنك/تأكيد دفع → إقفال، مع صلاحيات منفصلة وسجل تغييرات.
- إصلاح أخطاء التكرار وإعادة الحساب والقفل والـunpost/العكس بحيث لا يتكرر قيد الأستاذ العام أو يختلف المسير المعتمد بعد تعديل المصدر.
- **قبول:** إجمالي كل بند قابل للتفسير وإعادة التتبع، عزل صحيح، منع الاعتماد الذاتي حيث تتطلب السياسة، ومطابقة محاسبية مع ERP.

### المرحلة 5 — المغادرة أثناء الدوام ونهاية الخدمة

- طلب مغادرة قصيرة/تأخر/خروج مبكر بسير موافقات وتأثير محدد على الحضور، منفصل عن إنهاء الخدمة.
- إنهاء خدمة كحدث وسير عمل: السبب والنوع، تاريخ القرار وآخر يوم، الموافقات، العهد/المهام، إيقاف الحساب، الأجر حتى آخر يوم، السلف والاقتطاعات، الإجازة المستحقة/المصفاة، والاستحقاقات النهائية.
- الإنهاء والترحيل المالي معاملتان مترابطتان لكن لا تُغلقان قبل نجاح التحقق والترحيل؛ تحديد سياسة التعويض عن الفشل أو التراجع.
- **قبول:** لا حذف تاريخ الموظف؛ لا صرف/ترحيل مزدوج؛ التسوية قابلة للمراجعة وإعادة الشرح.

### المرحلة 6 — الإطلاق والتشغيل المتدرج

- تشغيل أولي على بيانات اختبار/عميل تجريبي، مطابقة كشوف الحضور والإجازة والراتب، مراجعة المستخدمين والصلاحيات، ثم ترحيل تدريجي.
- لوحات مراقبة لأخطاء مزامنة الموبايل، العمليات المعلقة، الحسابات المتكررة، وفشل الترحيل.
- إعداد النسخ الاحتياطي والاسترجاع، سجل التدقيق، تصدير بيانات العميل، وخطة إصلاح/تراجع لكل ترحيل قاعدة.

## قواعد موحدة لحركات Draft / Post / Unpost

هذه مبدأ مقترح يطبق بعد تحديد أنواع الحركات التي تحتاجه، لا إضافة عمود واحد عشوائياً لكل الجداول:

1. **Draft/Unposted:** قابلة للتحرير، لا تؤثر على الأرصدة أو الحسابات النهائية.
2. **Posted:** معتمدة، مؤرخة ومرتبطة بالمستخدم/المعتمد؛ يثبت معها أثر الحركة على السجلات التابعة.
3. **Unpost:** صلاحية مستقلة وسبب إلزامي؛ تنشئ عكساً/تعكس الآثار ذرياً إذا كانت الحركة لا تزال ضمن شروط العكس. الحركة المالية المرحلة قد تحتاج قيد عكسي في ERP بدلاً من مسح أثرها.
4. يمنع التعديل والحذف المباشر بعد post. يحتفظ سجل التدقيق بالحالة السابقة والجديدة والفاعل والوقت والسبب.
5. يجب أن تكون عمليات post/unpost آمنة عند التكرار، وتحترم إقفال الفترات، وتعالج تعارض الموافقات الذاتية وفق سياسة العميل.

## أسئلة القرار المفتوحة (الأعلى أثراً أولاً)

1. ما اسم/تفسير عزل الشركة الحالي في المشروع: CompanyId/Schema/قاعدة مستقلة؟ هل المقصود في جوابك الحفاظ على قواعده الحالية كما هي؟ نثبت ذلك من الكود ثم نستعمل الاصطلاح نفسه.
2. هل يسمح بموظفين غير مداومين أصلاً؟ وما الصفة الدقيقة التي تحدد تسجيل الحضور عبر الموبايل مقابل عدم الحاجة للحضور؟ هل تشمل موظفاً يعمل أونلاين من المنزل؟
3. إذا تداخل شفتان مؤقتان محددان للموظف، هل نمنع الحفظ أم نسمح بالأحدث إنشاءً/الأضيق فترة/الأعلى أولوية؟ وهل إسناد الشفت اليومي يتغلب على كليهما؟
4. وقت جهاز/موبايل الحضور بأي منطقة زمنية؟ للشفت الليلي، هل يوم الحضور هو تاريخ بداية الشفت؟ هذا افتراض عملي أولي، لكن ينبغي اعتماده مع التقارير والرواتب.
5. هل صلاحيات ERP الحالية تسمح بإنشاء أدوار ومنحها لكل عميل/فرع؟ من ينشئ المستخدم ويربطه بالموظف؟ هل المدير يحتاج رؤية فريقه فقط وموافقات أم إدارة موظفين؟
6. من يحق له post/unpost لكل نوع: HR، مسؤول راتب، محاسب؟ هل منشئ الحركة يمكنه اعتمادها؟ وما شرط unpost بعد ترحيل ERP أو إغلاق فترة؟
7. طلب missing punch: هل الطلب يُدخل وقتاً واحداً مفقوداً أم يمكن تصحيح الدخول والخروج معاً؟ هل يستطيع المدير إدخاله نيابة عن الموظف؟
8. ما البلدان/الكيانات القانونية وسياسات الضمان والضرائب؟ هل المسير لكل فرع أو شركة، وما الربط المطلوب مع دليل الحسابات والقيود البنكية في ERP؟
9. هل تشمل «كل مستحقاته المالية» في نهاية الخدمة مكافأة نهاية خدمة حسب سياسة/قانون البلد، تذاكر، عمولات، مستحقات غير مدفوعة، وتسوية سلف؟ من يعتمد الإقفال النهائي؟
10. ما التطبيق/واجهة الموبايل التي تستهلك API الحضور، وهل حدث الموبايل يرسل معرفاً فريداً ثابتاً لكل punch؟ هذه النقطة تحدد ضمان عدم التكرار عند إعادة المحاولة.

### قرارات أضيفت في 4 نوفمبر 2026

- **الأنواع الأساسية للإجازة:** سنوية، مرضية، وغير مدفوعة، مع السماح للشركة بإنشاء أنواع إضافية.
- **الأثر على الرواتب:** كل نوع إجازة يجب أن يحمل سياسة موثقة تؤثر على الأجر والرصيد. مبدئياً السنوية المدفوعة لا تخصم من الراتب، وغير المدفوعة تؤثر على الأجر، والمرضية ترتبط بسياسة الشركة والبلد؛ لا نفترض أنها مدفوعة بالكامل في كل حالة. الأنواع الإضافية تحتاج إعداداً واضحاً: مدفوعة/غير مدفوعة، هل تخصم رصيداً، وهل تدخل في احتساب أيام/أجر المسير.
- **التصميم المقترح:** إبقاء رموز أساسية ثابتة (مثل `ANNUAL`, `SICK`, `UNPAID`) وعدم ربط قواعد الرواتب باسم العرض العربي/الإنجليزي. الأنواع الإضافية تبقى قابلة للتهيئة ضمن مخطط العميل، مع إعدادات/سياسة صريحة. نراجع نموذج `LeaveType` الحالي قبل تعديل الحقول لأن `IsPaid` وحده لا يصف كل أثر الرواتب.
- **تعارض الشفت:** مبدئياً نرفض إسنادين مؤقتين متداخلين للموظف، ونسمح بإسناد أساسي مستمر مع إسناد مؤقت أعلى أولوية خلال نطاقه. يظل تعريف «تداخل التاريخ» وحدوده الدقيقة ضمن قواعد التحقق في API.
- **قرار مؤجل للإجازات:** كيف تُدفع الإجازة المرضية وما حدود الأيام/النسب؟ يختلف حسب البلد وسياسة العميل، ويجب حسمه قبل ربطها بحساب صافي الراتب.

## تصحيح نطاق السياسات — توجيه 4 نوفمبر 2026

- المنتج لا يفرض أنواع إجازة أو متطلبات قانونية/بلدية ثابتة. الشركة تحدد الأنواع والسياسات والقيم التي تريدها، ويمكنها عدم إنشاء نوع مرضي.
- أهلية بدء استحقاق الإجازة محسومة كإعداد لكل شركة: من تاريخ التعيين أو بعد مدة/شرط خدمة تختاره الشركة. وهي منفصلة عن منح كامل الرصيد مقدماً أو تراكمه سنوياً/شهرياً/يومياً.
- لا تدخل قواعد الدول أو التحقق من حد قانوني في تصميم المنتج بناءً على توجيه صاحب النظام.
- نقطة إعداد الإجازة الحالية تحتاج مقارنة تفصيلية بالمتطلبات؛ لا نطلب من المستخدم إعادة حسم أهلية البداية.

## أول حزمة عمل — إعداد سياسة الإجازة ورصيد الموظف (التصميم)

**الحالة:** تنفيذ أولي لحقول الإعداد وعقود الـAPI؛ قاعدة البيانات لم تُعدّل مباشرة.  
**الهدف:** تمكين كل شركة من ضبط أنواع الإجازات وأهليتها واستحقاقها وعرض رصيد مفهوم للموظف وHR.

### نموذج الإعداد المقترح

1. **نوع الإجازة (اختياري بالكامل لكل شركة):** رمز ثابت، اسم عربي/إنجليزي، نشط/غير نشط، مدفوع أو غير مدفوع، هل يتتبع رصيداً، هل يحتاج مرفقاً، وسياسة الترحيل والسقف. السنوية/المرضية/غير المدفوعة أنواع ابتدائية مقترحة وليست مفروضة.
2. **سياسة الاستحقاق لنوع الإجازة:** مقدار الاستحقاق السنوي المرجعي (قيمة واحدة في البداية)، أهلية تبدأ من تاريخ التوظيف أو بعد عدد أشهر خدمة، وطريقة الإضافة:
   - `YEARLY`: إضافة كامل الاستحقاق السنوي عند بداية دورة الاستحقاق (الرصيد متاح مقدماً).
   - `MONTHLY`: إضافة الاستحقاق السنوي مقسوماً على 12 على دفعات شهرية.
   - `DAILY`: إضافة الاستحقاق السنوي مقسوماً على 365/366 عن أيام السنة التقويمية المؤهلة.
   وتحدد السياسة هل يطبّق استحقاق نسبي على أول دورة عند أهلية الموظف في منتصفها.
3. **دورة السياسة:** إعداد يحدد بداية/تجديد الدورة: السنة التقويمية أو ذكرى التوظيف/تاريخ بدء الأهلية. تختارها الشركة لأن ذلك يغيّر توقيت المنح والرصيد لموظف بدأ وسط السنة.
4. **تنسيق عرض الرصيد لكل شركة:** `DECIMAL` أو `DHM` (أيام/ساعات/دقائق). الحساب والتخزين يبقيان بالأيام العشرية، والتحويل إلى الوقت يستخدم ساعات يوم العمل القياسي المضبوطة للشركة/التقويم.
5. **أثر الراتب:** إعداد مدفوع/غير مدفوع مستقل عن تتبع الرصيد؛ لا نربط `IsPaid` تلقائياً بوجود رصيد. إجازة بلا رصيد قد تكون مدفوعة، أو إجازة تتبع الرصيد قد تكون لها طريقة دفع تختارها الشركة. نحدد mapping صريحاً لاستهلاك الأيام والاقتطاع قبل تمريرها للمسير.

### واجهات/API القائمة التي نعيد استخدامها أو نطورها

- `GET /api/hr/leaves/balances/{employeeCode}` موجود: نوسّع/نصحح الرد ليعرض الأنواع التي أعدتها الشركة والرصيد المكتسب فعلياً، المستخدم، المعلّق، المرحّل، والمتبقي المتاح، مع تفضيل العرض. تجنب fallback الحالي الذي قد يعرض `MaxDaysPerYear` كامل الرصيد قبل اكتسابه.
- `POST /api/hr/leaves/types` و`PUT /api/hr/leaves/types/{code}` موجودان لإدارة أنواع العميل؛ أضيف حقل `TracksBalance` منفصلاً عن `IsPaid` إلى عقد النوع.
- `GET/POST /api/hr/leaves/policies` موجودان؛ أضيفت عقود الحصة السنوية الصريحة، ودورة الاستحقاق، والاستحقاق النسبي لأول دورة مع الحفاظ على حقول الشرائح القديمة.
- `POST /balances/accrue-monthly` و`/balances/yearly-grant` موجودان كعمليات يدوية. نجعلهما يستندان إلى إعداد السياسة أو نستبدل التشغيل اليدوي بمهمة آمنة؛ لا نعتمد تراكم DAILY قبل منع التكرار.

### الأثر البياني المقترح قبل التنفيذ

- الاحتفاظ برصيد سنوي مُلخّص للقراءة السريعة، وإضافة دفتر حركات رصيد لكل اكتساب/استخدام/ترحيل/تصحيح/عكس مع التاريخ والسبب والمنفذ والمصدر. يمنحنا ذلك حماية من تكرار مهمة شهرية/يومية ويتيح تفسير الرصيد.
- تقييد السياسة بتاريخ سريان، ومنع وجود سياستين متداخلتين لنوع الإجازة/نطاق الموظفين نفسه إلا إذا أُضيفت أولوية صريحة.
- عدم فرض حقول `CompanyId` إذا كان Schema-per-company كافياً، والالتزام بإضافة الجداول والأعمدة إلى `DEV_TEMPLATE` ثم مزامنتها حسب إجراء النشر.

### إعداد مرن بدلاً من قرار عام موحد

لا نطلب من الشركة قاعدة واحدة مشتركة: دورة الاستحقاق (سنة تقويمية/ذكرى التوظيف) والاستحقاق النسبي لأول دورة كلاهما إعدادان لكل سياسة. نبدأ بقيمة افتراضية يحددها العميل عند تفعيل السياسة، ونحفظ تغييرات السياسة بتاريخ سريان.

### معايير قبول الحزمة

- يمكن للشركة إنشاء نوع مرضي أو عدم إنشائه، وإنشاء أنواع إضافية بلا تغيير كود.
- يمكن إعداد entitlement سنوي واختيار أهلية وتواتر المنح وتنسيق العرض.
- يظهر API الرصيد القيم الفعلية حتى تاريخ محدد ولا يمنح الحصة السنوية كاملة افتراضياً.
- إعادة تشغيل مهمة الاستحقاق لا تضاعف الأرصدة؛ كل حركة قابلة للتدقيق والتفسير.
- إنشاء/اعتماد طلب إجازة يخصم من الرصيد مرة واحدة وفق الإعداد، وتظهر قيمة المعلّق والمتبقي بصورة صحيحة.

### سجل التنفيذ الأولي (4 نوفمبر 2026)

- أضيف `TracksBalance` لنوع الإجازة مع قيمة متوافقة للأنواع الحالية، وفُصل عن `IsPaid` في طلب/اعتماد الإجازة وعرض الأرصدة. تحديث النوع من عميل API قديم لا يغير إعداد تتبع الرصيد إذا لم يرسل الحقل.
- أضيفت حقول سياسة `AnnualEntitlementDays`, `CycleBasis`, `ProrateFirstCycle` إلى الكيان وDTO، والتحقق من قيمة الطريقة والدورة، وربط الحصة السنوية وحد الخدمة والتناسب بمنح الرصيد الشهري/السنوي اليدوي.
- وسعت `HrSchemaTool --repair` لإضافة أعمدة نوع الإجازة والسياسة المفقودة إلى `DEV_TEMPLATE`؛ مزامنة التغيير لمخططات العملاء تمر عبر مسار schema sync المعتمد. لم أشغّل أداة الإصلاح ولم أغير قاعدة البيانات.
- **لم يكتمل بعد:** التراكم اليومي والتشغيل التلقائي، تطبيق دورة ذكرى التوظيف، دفتر حركات الرصيد ومنع التكرار، إعداد عرض `DECIMAL/DHM`، وتصحيح fallback الحالي الذي قد يعرض الحد السنوي كاملاً قبل اكتسابه. لا تعتمد إعداد DAILY أو دورة الذكرى كحساب تشغيلي مكتمل إلى حين إتمام المحرك.
- بناء `ThinkOnErp.Application` نجح مع تحذيرات موجودة. تعذر بناء Infrastructure وتوليد migration بـEF بسبب فشل MSBuild أثناء استكشاف مراجع المشروع دون أخطاء C#؛ لهذا اتبعنا نمط أداة `HrSchemaTool` الحالية لتعديل DEV_TEMPLATE مستقبلاً. لم أشغّل اختبارات أو تحديث قاعدة بيانات.

## سجل فحص المرحلة 0 — عزل HR (4 نوفمبر 2026)

- وثائق المعمارية في `docs/modules/README.md` تصف Schema Routing وDedicated Company Schemas. إذن عزل العملاء الأساسي هو مخطط مستقل لكل شركة؛ وجود `CompanyId` على كيان داخل المخطط ليس شرطاً بحد ذاته لإثبات العزل.
- `OracleDbContext` يطبق أيضاً نطاق HR بحسب الفروع على الموظفين، ثم يربط نطاق عدد من جداول HR بالموظفين أو بـ`CompanyId`. هذه طبقة تضييق/حماية إضافية داخل مخطط الشركة.
- صاحب النظام أكد أن تعريف الشفت خاص بالعميل. `ShiftSchedule` لا يحمل `CompanyId` أو `EmployeeCode` ومفتاحه `ShiftCode` فقط. **هذا ليس دليلاً كافياً على تسرب بين العملاء** في معمارية المخططات المنفصلة؛ المتوقع أن يكون لكل مخطط عميل نسخة مستقلة من الجدول. يجب التأكد أن مخططات العملاء تُنسخ من `DEV_TEMPLATE`، وأن جميع عمليات القراءة والكتابة تتم عبر مخطط الشركة المختار، لا عبر مخطط القالب أو مخطط ثابت.
- `EmployeeShiftAssignment` يملك `EmployeeCode`، لذلك يستفيد من فلتر الموظف داخل نطاق HR؛ وعند كتابة API الإسناد يجب التحقق من نطاق الفرع ومن وجود الموظف والشفت في مخطط الشركة الحالي. النموذج لا يسجل أولوية ولا يحسم تعارض فترتين مؤقتتين.
- **المعالجة:** لا نضيف `CompanyId` تلقائياً ولا ننفذ migration الآن. في جرد المرحلة 0 نتتبع مسار اختيار المخطط في API→DbContext، ومزامنة مخططات العملاء من القالب، ثم نستكمل العلاقات والقيود الخاصة بالإسناد. لا تغيير كود في هذا الفحص.
- فحص تدفق الشفت والحضور: `ShiftSchedule` و`EmployeeShiftAssignment` معرفان في EF وموجودان في migration، لكن البحث في خدمات/API لم يظهر استخداماً لإسناد الموظف عند حساب يوم الحضور أو CRUD/إسناد API. `AttendanceCalculationEngine` يستقبل `shiftStart/shiftEnd` اختيارياً ويستخدم افتراض 08:00–17:00 عند غيابهما؛ خدمة الموبايل تسجل RawAttendance وتحدّث AttendanceDay مباشرة، ولا يظهر أنها تختار الشفت المسند.
- **ترتيب المعالجة:** قبل واجهات الشفت، نبني خدمة واحدة لاختيار الشفت الساري للموظف/التاريخ ثم حساب الحضور منها، ونمرر لها سياسة المنطقة الزمنية واليوم الليلي بعد اعتمادها. بعد ذلك نضيف API الإدارة والإسناد وجدولة اليوم ونوصل بها الموبايل. لا نكرر منطق حساب الحضور داخل مسار الموبايل ومسار معالجة الأجهزة.
- تغييرات `DEV_TEMPLATE` تنسخ إلى مخططات العملاء من خلال خدمة `SyncTenantSchemaAsync`؛ لكن لم يتم تنفيذ sync فعلي أو فحص كل الشركات في هذه المراجعة. شرط قبل إطلاق جداول/أعمدة جديدة: اختبار sync على نسخة تجريبية والتحقق من الترحيل وعدم تغيير بيانات العملاء.
- لا كود أو قاعدة بيانات عُدّلت في مراجعة الشفت؛ هذه نتائج قراءة المستودع فقط.
- صاحب النظام وضّح أن سياسة الإجازة تحدد أولاً الاستحقاق السنوي المرجعي (مثلاً 14 أو 21 يوماً أو قيمة أخرى للشركة)، ثم طريقة منحه: سنوي دفعة واحدة، أو شهرياً على أجزاء، أو تراكم يومي. قيمة الاستحقاق السنوي وتواتر المنح إعدادان منفصلان.
- صاحب النظام وافق على تنظيم إعدادات HR في أقسام مترابطة: بيانات وتنظيم الموظف؛ الدوام (التقويم والعطل والشفتات والجدول اليومي)؛ الحضور؛ الإجازات؛ الرواتب؛ والربط المحاسبي والتكاملات.
- عند التراكم اليومي يجب أن تحدد السياسة هل المقام أيام السنة التقويمية أم أيام العمل المجدولة، وكيف تحسب الأيام الجزئية للموظف الجديد، وهل يظهر الاستحقاق كحركة يومية مجدولة أم يحسب accrued-to-date عند القراءة. يبقى هذا قراراً مطلوباً قبل التنفيذ.
- **حُسم في 4 نوفمبر 2026:** الاستحقاق اليومي يعتمد أيام السنة التقويمية. قاعدة الحساب المقترحة: الحصة السنوية ÷ عدد أيام سنة الاستحقاق (365 أو 366 في السنة الكبيسة)، وتراكمها بحسب أيام أهلية الموظف في تلك السنة. يبقى تحديد تاريخ بدء الأهلية (تاريخ التعيين أو بعد مدة خدمة دنيا/فترة تجربة حسب سياسة العميل) تابعاً لإعداد السياسة.
- **توضيح أهلية ومنح الرصيد:** كل عميل يختار نقطة بدء الأهلية (من تاريخ التعيين أو بعد مدة/شرط خدمة)، وبشكل مستقل يختار طريقة الإتاحة: منح كامل الرصيد مقدماً عند بدء الاستحقاق/بداية السنة، أو تراكمه سنوياً، شهرياً، أو يومياً. يجب تعريف prorating لأول/آخر سنة حسب السياسة، والتمييز في شاشة الرصيد بين المستحق السنوي الكامل، المكتسب حتى اليوم، المستخدم، المعلّق، المتبقي القابل للاستخدام، والمرحّل.
- **المرضية:** الشركة تنشئ نوع الإجازة المرضية وتحدد قواعده عند الحاجة؛ لا يضيف المنتج قوالب قانونية أو قيوداً حسب البلد.
- **مالك الإعدادات:** المدير أو أي مستخدم يمنحه المدير صلاحية HR Setup؛ هذا يستخدم نظام الأدوار/الصلاحيات الحالي ولا يتطلب دور HR ثابتاً جديداً إلا إذا كشف تدقيق الصلاحيات عن نقص.
- **الجدول اليومي للشفتات:** يدعم إدخال/إسناداً يومياً مباشراً، وكذلك توليد الجدول من الشفت الأساسي والمؤقت ثم السماح بتعديل أيام بعينها. أولوية الشفت المؤقت على الأساسي، ورفض التداخل المؤقت كما اتُّفق، مع نسبة الوردية الليلية لتاريخ بدايتها.
- فحص أثر الإجازة على الرواتب: الأنواع قابلة للإضافة/التعديل حالياً عبر `LeavesController`، و`LeaveType` فيه `IsPaid` وحد سنوي وترحيل ومستندات. الطلبات المدفوعة تفحص الرصيد وتخصم `UsedDays` عند الموافقة. محرك الراتب يجمع الإجازات المعتمدة لكل الأنواع غير المدفوعة ويحسب خصم `UNPAID_LEAVE` على الأساسي. هذا يعطي أساساً للسنوية/غير المدفوعة، لكنه يعني أن أي نوع مخصص يضبط `IsPaid=false` سيعامل كخصم راتب؛ كما أن المرضية المدفوعة ستستخدم منطق رصيد النوع نفسه. نحتاج تأكيد سياسات المرضيّة والأنواع الإضافية قبل اعتماد الحساب.
- **قرار المستخدم:** ثلاث فئات أساسية ثابتة: سنوية، مرضية، وغير مدفوعة؛ ويجوز للشركة إضافة أنواع أخرى. نحافظ على رموز عمل ثابتة للفئات الأساسية (لا ربط بالاسم المترجم)، ونراجع هل يلزم نوع سياسة/أثر راتب أدق من `IsPaid` قبل توسيع المسير.
- **قرار المستخدم:** عند تداخل شفتين مؤقتتين لموظف واحد، يرفض الإسناد مؤقتاً حتى تتضح القاعدة الأفضل. يبقى الشفت المؤقت غير المتعارض أعلى أولوية من الشفت الأساسي المستمر.
- **قرار المستخدم:** يلزم جدول يومي يسند شفتاً لموظف في تاريخ محدد، بالإضافة إلى قواعد الشفت الأساسي/المؤقت.
- **قرار المستخدم:** يريد الموظف/HR رؤية الرصيد الحالي والمستخدم على الأقل للإجازة السنوية والمرضية؛ طريقة العرض تُضبط لكل شركة (عدد عشري أو أيام/ساعات/دقائق).
- **قرار المستخدم:** استحقاق الرصيد قد يكون سنوياً أو شهرياً أو يومياً حسب إعداد الشركة، ويجب أن يضاف تلقائياً لكل موظف وفق السياسة.
- **API الرصيد الموجود حالياً:** `GET /api/hr/leaves/balances/{employeeCode}` يعرض `AccruedDays`, `UsedDays`, `CarriedForwardDays`, `RemainingDays` ويأخذ سنة اختيارية، لكنه يعيد أنواع الإجازات المدفوعة فقط. إذا لم يوجد رصيد محفوظ، يستخدم `LeaveType.MaxDaysPerYear` كـ`AccruedDays`؛ وهذا قد يعرض كامل الحصة السنوية كرصيد حالي حتى عند سياسة استحقاق شهري/يومي. نحتاج تغيير معنى fallback إلى رصيد مكتسب فعلياً وفق السياسة والتاريخ، وإرجاع السنوية/المرضية بحسب إعداد الرصيد حتى لو كان نوعاً غير مدفوع جزئياً.
- توجد عمليات API يدوية للاستحقاق الشهري والتخصيص السنوي، وسياسة `LeavePolicy.AccrualMethod` تعرف `YEARLY`, `MONTHLY`, `PRO_RATA`. لم يظهر خيار `DAILY` ولا تشغيل خلفي تلقائي موثق. التنفيذ الشهري الحالي يحسب معدل الحصة السنوية/12 حتى لو وُجدت قيمة `AccrualMethod` مختلفة؛ يلزم توحيد التنفيذ مع الإعداد ومنع التكرار.
- **وحدة العرض:** لا نغير وحدة التخزين الأساسية (أيام عشرية) لهذا الطلب؛ نضيف إعداد عرض على مستوى الشركة في إعدادات HR: `DECIMAL` أو `DHM`. تحويل D/H/M يتطلب عدد ساعات العمل القياسي في اليوم من التقويم/سياسة الشركة؛ يجب ألا نفترض دائماً 8 ساعات.

## تنفيذ أولي — قراءة رصيد الإجازة المكتسب

**الحالة:** منفذ في كود الخدمة؛ بناء مشروع Application ناجح. لم تُشغّل اختبارات أو تغييرات قاعدة بيانات.

- أضيف `TracksBalance` لنوع الإجازة حتى لا تختلط أهلية تتبع الرصيد مع كون النوع مدفوعاً. أنواع العميل التي لا تتبع رصيداً لا تظهر ضمن endpoint الأرصدة.
- أضيفت إعدادات السياسة: الحصة السنوية الصريحة، أساس الدورة (`CALENDAR_YEAR` أو `EMPLOYMENT_ANNIVERSARY`) وخيار التناسب لأول دورة، مع إبقاء حقول الشرائح القديمة للتوافق.
- Endpoint الرصيد الحالي يقرأ السياسات النشطة ويحسب fallback المكتسب عند عدم وجود صف رصيد: `YEARLY` يمنح الحصة عند الأهلية، و`MONTHLY` يتناسب مع الأيام المؤهلة في كل شهر، و`DAILY` يتناسب مع الأيام التقويمية المؤهلة على مقام 365/366 (أو طول دورة ذكرى التوظيف). إذا وجد صف رصيد محفوظ، يبقى هو المصدر authoritative ويُعرض كما هو.
- لا يزال التشغيل التلقائي الدوري غير موجود؛ fallback أعلاه للقراءة فقط. المنح الشهري صار يحسب الفرق حتى استحقاق الشهر المطلوب، فيمنع تكرار الإضافة عند إعادة الطلب بالتتابع؛ التزامن بين طلبين لا يزال يحتاج قيداً/دفتر حركات لضمان idempotency الكامل قبل الجدولة الآلية.
- تاريخ «حتى اليوم» في القراءة يستخدم UTC مؤقتاً لعدم وجود إعداد منطقة زمنية للشركة موصول بهذه الخدمة؛ قبل التشغيل الفعلي يجب ربطه بتوقيت العميل حتى لا يتغير تاريخ الاستحقاق عند حدود اليوم/السنة.
- لم يكتمل إعداد عرض `DECIMAL`/`DHM` ولا تحويل ساعات/دقائق؛ الرد الحالي يبقى بالأيام العشرية. كذلك يلزم حساب الرصيد المعلّق، التعامل مع اعتماد/إلغاء الطلب كحركات متوازنة، واختبار حالات السنة الكبيسة والدورة السنوية بعد تثبيت المقصود من أول دورة.
- دورة ذكرى التوظيف مطبقة حالياً في حساب fallback عند القراءة فقط؛ نموذج `LeaveBalance.YearNo` وعمليات المنح المحفوظة ما زالت مبنية على سنة رقمية، لذلك لا نعتبر دورة ذكرى التوظيف أو سنة مالية تبدأ في شهر مخصص مدعومتين بالكامل قبل تغيير مفتاح دورة الرصيد.
- قاعدة البيانات لم تتغير. أضيفت أعمدة/إصلاحات مخطط إلى أداة `HrSchemaTool` التي تستهدف `DEV_TEMPLATE` فقط؛ يجب مراجعة SQL الناتج ثم تشغيلها على نسخة تطوير ومزامنة مخطط عميل تجريبي قبل أي نشر.

## متابعة التنفيذ — دورة الإجازة والتزامن وإعداد العميل

**الحالة:** أضيفت إلى الكود؛ لا توجد تغييرات قاعدة بيانات منفذة.

- أضيف إعداد شركة عبر `GET/PUT /api/hr/leaves/settings`: شهر/يوم بداية سنة الإجازة، وطريقة عرض الرصيد `DECIMAL` أو `DHM`. يتطلب `DHM` ساعات يوم عمل مضبوطة بين 0.25 و24؛ لا يوجد افتراض ثابت لثماني ساعات.
- السياسة تقبل `COMPANY_LEAVE_YEAR`. كل دورة غير ذكرى التوظيف تستخدم إعداد بداية سنة الشركة، حتى مع قيمة السياسة القديمة `CALENDAR_YEAR` للحفاظ على التوافق. `EMPLOYMENT_ANNIVERSARY` يظل دورة مستقلة للموظف.
- `LeaveBalance.YearNo` أصبح سنة بداية الدورة، وأضيف تاريخا بداية ونهاية الدورة للحفظ والرد. التقديم والموافقة والمنح والقراءة تستخدم تاريخ الدورة، ويُرفض طلب إجازة يمتد عبر حد الدورة ليُقسّم إلى طلبين.
- المنح الشهري والسنوي أصبح «تحديثاً إلى المستحق حتى التاريخ» بدلاً من زيادة تراكمية عمياء؛ يقفل سجل الموظف داخل معاملة Oracle ويكتب الفرق مرة واحدة. هذا يجعل إعادة الطلب المتزامنة أو المعادة آمنة على قيمة الرصيد من دون ledger منفصل، مع إبقاء القيود الفريدة كحماية أخيرة.
- دقة أيام الرصيد صارت أربع منازل عشرية لتناسب التراكم اليومي. `HrSchemaTool --repair` يضيف أعمدة تواريخ الدورة وجدول إعدادات العميل، يوسع الدقة، ويستبدل القيد الفريد من `(الموظف، النوع، YearNo)` إلى `(الموظف، النوع، تاريخ بداية الدورة)`؛ لم تُشغّل الأداة.
- صفوف الأرصدة القديمة ذات تاريخ دورة فارغ تُقرأ كصفوف سنة ميلادية. ولمنع نقل رصيد قائم إلى دورة مختلفة بصمت، يرفض API تغيير شهر/يوم بداية السنة إذا وجدت أرصدة. يلزم إجراء ترحيل افتتاحي قابل للمراجعة قبل السماح بتغيير السنة لعميل لديه أرصدة.
- أضيفت حقول عرض `DHM` للرصيد المكتسب والمستخدم والمرحّل والمتبقي، مع إبقاء القيم الرقمية بالأيام كما هي.
- **التحقق:** `ThinkOnErp.Application` بُني دون أخطاء (تحذيرات موجودة مسبقاً)، ولم تُشغّل اختبارات. تعذر بناء Infrastructure/API من MSBuild قبل مرحلة C# بسبب تعذر حل `Microsoft.NET.SDK.WorkloadAutoImportPropsLocator` و`Microsoft.NET.SDK.WorkloadManifestTargetsLocator` في SDK المحلي؛ لا يوجد خطأ C# ظاهر، لكن هذين المشروعين غير متحققين بالبناء في هذه الجلسة.

## إضافة إلى النطاق — سنة الإجازة وإقفالها

**الحالة:** الإعداد العام ودورة الرصيد وسير المسودة/الترحيل/العكس منفذة أولياً. لا تغيير قاعدة بيانات منفذ.

- لكل شركة إعداد بداية سنة الإجازات (شهر/يوم)، مستقلاً عن السنة الميلادية؛ مثال: تبدأ في 1 سبتمبر. حساب الاستحقاق اليومي يعتمد طول سنة الاستحقاق الفعلية (365/366) بعد تحديد هذه الدورة، ونراجع التغيير من `CALENDAR_YEAR` الحالي إلى دورة ذات تاريخ بداية مخصص.
- سياسة الإقفال الحالية تستخدم حقول النوع الموجودة للترحيل الكامل/بسقف، وأضيف `YearEndExcessAction`: `EXPIRE` أو `REQUIRE_USE` أو `CASHOUT`. `REQUIRE_USE` يمنع إنشاء المسودة إذا بقيت أيام غير مستخدمة، كما يمنع وجود طلبات إجازة معلقة خلال الدورة؛ `EXPIRE` يسقط الفائض عند الترحيل؛ و`CASHOUT` يسجل أيام التسوية في المسودة.
- المسارات الجديدة: `POST /api/hr/leaves/balances/year-end-close/draft` لإنشاء/تحديث مسودة؛ `GET /api/hr/leaves/balances/year-end-close/{id}` للمراجعة؛ ثم `POST .../{id}/post` و`POST .../{id}/unpost`. الإقفال يحفظ لقطة الرصيد لكل سجل، يقفل الموظفين داخل معاملة، ويمنع تكرار POST. UNPOST يعيد القيم السابقة فقط إذا لم تتغير أرصدة المصدر/الهدف منذ الترحيل.
- المسار القديم `POST /balances/year-end-rollover` ما زال متاحاً كتوافق، لكنه ينشئ المسودة ثم يرحلها مباشرة ويتطلب صلاحية `post`.
- يمكن تحديث مسودة `DRAFT` أو إعادة تجهيز `UNPOSTED` بعد تصحيح الأرصدة؛ المسودة الجديدة تمسح تفاصيلها السابقة وتعيد اللقطة، بينما الإقفال `POSTED` يظل ثابتاً ولا يعاد حسابه.
- يعاد فحص طلبات الإجازة المعلقة عند `POST` أيضاً، وليس عند تجهيز المسودة فقط، وتُقفل سجلات الموظفين قبل تطبيق الأثر. هذا يقلل نافذة التغيير بين مراجعة المسودة واعتمادها.
- تحديث المسودة نفسها يأخذ قفل قاعدة بيانات على رأس الإقفال ويعيد قراءة حالته قبل استبدال التفاصيل؛ فلا يمكن لمسودة متزامنة أن تستبدل لقطة إقفال منشورة.
- **حد الإقفال الحالي:** أيام `CASHOUT` تظهر محفوظة في المسودة، لكن `POST` يرفضها حتى تُحسب قيمة النقد وتُربط بمسير رواتب معتمد وقيد محاسبي. لا نرحل مبلغاً نقدياً أو نختار أساس احتسابه نيابة عن الشركة.
- يلزم ترحيل مخطط `HrSchemaTool --repair` لإضافة جدولي رأس الإقفال وتفاصيله وحقل إجراء الفائض. يجب التحقق من أرصدة العملاء القدامى على DEV_TEMPLATE وعميل تجريبي قبل تشغيلها؛ لم تُشغّل الأداة.
- لا تزال سياسة الاستهلاك الإلزامي تمثل شرطاً قبل إنشاء المسودة فقط؛ لم نضف تنبيهاً مسبقاً أو منعاً لحجز إجازة جديدة على رصيد سابق. كذلك يحتاج سجل محاولات POST/UNPOST المتكرر إلى مراجعة الـAudit middleware عند اختبار الـAPI.

## الخطوة التالية المنفذة — اعتماد تعديلات الرواتب

- الحركات الجديدة في `HR_PAYROLL_ADJUSTMENT` تبدأ `PENDING` بدلاً من اعتمادها تلقائياً. الأرصدة والحركات القديمة لا تتغير بهذا التعديل.
- مسار `approve` الحالي باقٍ بصلاحية الاعتماد. أضيف `POST /api/hr/adjustments/{id}/post` بصلاحية `post`، و`POST .../{id}/unpost` بصلاحية `reverse` لإرجاع حركة `APPROVED` إلى `PENDING`.
- الاعتماد والرفض مسموحان لحركة معلقة فقط؛ حذف المعتمدة يتطلب إلغاء اعتمادها أولاً. الحركة المرتبطة بسطر مسير أو حالتها `PROCESSED` محمية من هذه التغييرات.
- يفحص النظام أيضاً وجود مسير محسوب للموظف والفترة؛ لأن الرابط `PayrollRunLineId` ليس معبأ دائماً حالياً. وجود مسير غير مسودة وغير ملغى يمنع تغيير الاعتماد أو حذف الحركة حتى إلغاء الحساب. هذا فحص تحفظي على مستوى الموظف/الفترة.
- أضيف تحقق المبلغ الموجب ونوع الحركة `EARNING/DEDUCTION` والحقول الإلزامية، وعلامتا optimistic concurrency على حالة الحركة ورابط المسير من دون أعمدة جديدة.
- رُبط حساب المسير واعتماد/رفض/إلغاء اعتماد/حذف تعديلات الرواتب بقفل مشترك على فترة الشركة داخل معاملة `ReadCommitted`. تحتفظ العملية بالقفل حتى حفظ الحساب أو الحركة وإتمام المعاملة؛ ويعيد تعديل الحركة قراءتها بعد القفل قبل فحص حالتها والمسير. إنشاء تعديل جديد يظل معلّقاً فلا يدخل الحساب دون اعتماد.
- استخدام `ReadCommitted` هنا مقصود لقراءة آخر تغييرات العملية السابقة بعد الانتظار على قفل Oracle؛ لا يُستخدم snapshot قديم من معاملة Serializable لهذا المسار. الفترات غير المنشأة ترفض العملية بدلاً من حساب مسير دون قفل.

- نجحت الاختبارات الاثنان والثلاثون في المجموعة المحدودة، ونجح بناء API وجميع مشاريعه المرجعية. اختبارات Oracle الفعلية وتطبيق عمود الإعداد ومزامنة العملاء لم تُنفذ.

## متابعة — إلغاء الحساب وإعادة حساب المسير دون ازدواج

- أضيف `POST /api/hr/payroll/{id}/cancel` بصلاحية `reverse`، مع جسم طلب `{ "reason": "سبب الإلغاء" }`. يقبل مسيراً `DRAFT` أو `CALCULATED` قبل الاعتماد والأثر المحاسبي، ويحفظ اسم المستخدم والتاريخ والسبب. لا يحذف السطور أو مبالغها أو لقطة شرح الحساب، ويظهر `Status` وبيانات الإلغاء في رد عرض المسير.
- عملية الإلغاء تشارك قفل فترة الرواتب مع الحساب والاعتماد وتعيد قراءة المسير بعد القفل. تكرار إلغاء مسير `CANCELLED` يعيد نتيجته من دون إنشاء أثر أو تغيير سبب الإلغاء الأصلي.
- يمنع الإلغاء عند وجود ربط بتسويات قروض أو تعديلات، أو فترة مغلقة، أو اعتماد/قيد محاسبي. إلغاء اعتماد المسير المالي يحتاج عكس تسويات القروض والسلف والقيد في سير مستقل؛ لا تعكس هذه العملية تلك الآثار.
- حساب المسير يرفض وجود أي مسير نشط للفرع والفترة، بما فيه مسير محسوب أو معتمد. البحث عن المسير النشط يتجاهل الملغى. بعد الإلغاء يمكن تصحيح المدخلات ثم استدعاء `/calculate` لإنشاء مسير جديد، مع بقاء الملغى للتدقيق. الاعتماد يتطلب `CALCULATED` ويرفض وجود مسير نشط آخر حتى لو كانت البيانات القديمة تتضمن نسخاً متعددة.
- مُنع تصدير المسير الملغى إلى البنك. شروط تصدير الحالات الأخرى وصلاحية معاينة التصدير تبقى بند مراجعة منفصلاً في خطة ربط الدفع.
- الحماية من الحساب المكرر موجودة في طبقة الخدمة تحت قفل الفترة، ولا تضيف قيد Oracle فريداً شرطياً على الحالات؛ الكتابة المباشرة أو تكامل يتجاوز الخدمة يحتاج التزاماً بالعقد نفسه.
- أضيفت أعمدة الإلغاء الثلاثة nullable إلى mapping وأداة إصلاح HR؛ الأداة لم تُشغّل وقاعدة البيانات لم تتغير. يلزم نشر الأعمدة قبل تشغيل هذا الإصدار على قاعدة موجودة.
- أضيفت اختبارات لحفظ مبالغ/لقطة المسير عند الإلغاء، وثبات أثر إعادة الطلب، ورفض الحالات المالية والروابط التابعة، ومنع الحساب المكرر وتصدير الملغى.
- نجح بناء API ومشاريعه المرجعية، ونجحت الاختبارات التسعة والثلاثون في المجموعة المحدودة. لم تُنفذ تغييرات قاعدة بيانات أو اختبارات تزامن Oracle حقيقية.

## متابعة — حماية تصدير الرواتب البنكي

- التصدير والمعاينة يتطلبان صلاحية `hr-payroll/export`. المعاينة تعيد بايتات ملف التصدير، ولذلك لا تكفي صلاحية العرض وحدها. يولد الملف لمسير `APPROVED` أو `POSTED_TO_GL` أو `PAID`؛ المسودة والمحسوب والملغى مرفوضة.
- تُستبعد حركات `CASH` والأجر الصفري/السالب، ويُرفض أسلوب دفع غير معروف بدلاً من إدخاله كتحويل بنكي. يُرفض ملف بلا دفعات بنكية موجبة أو بدفعات مكررة للموظف أو بسطور ملغاة.
- أضيفت لقطة العملة واسم المستفيد ورقمه التعريفي إلى سطر الحساب (`CurrencyCode`, `BeneficiaryName`, `BeneficiaryNationalId`). الحساب الجديد يحفظها؛ التصدير يستخدمها مع IBAN ورمز البنك المحفوظين في السطر، ولا يستبدل بيانات دفع ناقصة من ملف الموظف الحالي. الرقم التعريفي ليس شرطاً عاماً مفروضاً؛ متطلبات البنك الخاصة تحتاج ملف إعداد للبنك.
- العملة تأتي من هيكل الراتب؛ CSV لم يعد يفرض JOD. الملف الواحد يتطلب عملة واحدة حتى لا يكون مجموع المبالغ مضللاً. الدفع بعملات متعددة يحتاج دفعات منفصلة/مرشح عملة في مرحلة تالية.
- صيغ التصدير غير المعروفة تُرفض عوض الرجوع الصامت إلى CSV. أرقام المبالغ تكتب بثقافة ثابتة، وكل حقول CSV النصية تُقتبس مع تهريب علامات الاقتباس. القوالب ذات الفاصل `|` ترفض فواصل/أسطر مزروعة داخل القيم.
- قوالب `RAWATEBKOM/WPS/SIF` الموجودة تبقى قوالب قديمة محدودة بـJOD، ولا تعني هذه التعديلات تصديقها من البنك أو مطابقتها لجميع البلدان. ربط قالب بنك فعلي يحتاج مواصفاته وحساب الشركة وأسلوب تعريف البنك والتحقق من IBAN وفق ذلك القالب. CSV عام للمراجعة ولا يشكل أمراً مصرفياً مرسلاً.
- أضيفت أعمدة snapshot الثلاثة nullable إلى mapping وأداة الإصلاح ولم تطبق على قاعدة البيانات. السجلات القديمة التي لا تحمل العملة/اسم المستفيد تحتاج تصحيح لقطة تاريخية موثوقاً أو إعادة حساب عبر سير الرواتب؛ لا تخمّن الأداة العملة أو تفاصيل المستفيد من السجل الحالي.
- أضيفت اختبارات لحالات الاعتماد، واستبعاد النقدي، وثبات بيانات المستفيد عند تعديل ملف الموظف، ورفض نقص بيانات اللقطة/تعدد العملات/صيغة غير معروفة، وتنسيق CSV تحت ثقافة تستخدم الفاصلة العشرية. اختبارات القوالب السابقة أُدرجت في المجموعة المحدودة وتحدّثت عيناتها لتحمل اللقطة المطلوبة.
- نجحت الاختبارات الأربعة والخمسون في المجموعة المحدودة. لا تشمل اختبار صلاحيات HTTP فعلياً أو اعتماد ملف من بنك أو اختبار Oracle متكامل، وقاعدة البيانات لم تتغير.
- أضيفت أربعة اختبارات لدورة اعتماد التعديل ومنع حذف المعتمد أو عكس حركة مستخدمة في المسير. بناء Application ناجح؛ محاولة تشغيل الاختبارات المفلترة توقفت في مرحلة البناء بلا نتيجة تنفيذ، لذلك لا تعتبر الاختبارات ناجحة أو مرحلة Infrastructure/API متحققة بعد. لم تنفذ تغييرات قاعدة بيانات.
