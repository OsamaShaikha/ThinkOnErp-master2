# دفتر حركات رصيد الإجازة — LEV-10

**تاريخ الحزمة:** 5 نوفمبر 2026. نُفذ الكود وAPI القراءة، وأُضيف الجدول والحماية إلى DEV_TEMPLATE بعد نسخة محلية. لم يُنشر التطبيق ولم تُزامن مخططات العملاء الأخرى.

## ما يسجله الدفتر

كل حركة تحفظ الموظف والنوع وبداية الدورة ورقم الرصيد، وتسلسلاً داخل الرصيد، ونوع الحركة والمصدر والسبب والفاعل ووقت التسجيل UTC. تحفظ دلتا المكتسب والمستخدم والمرحّل، والقيم الثلاث بعد الحركة. تغير المتاح = دلتا المكتسب + دلتا المرحّل − دلتا المستخدم.

| النوع | الأثر والمصدر |
|---|---|
| OPENING_SNAPSHOT | الرصيد الذي رُصد عند بدء تسجيل حركات هذا الرصيد، بقيمه المحفوظة آنذاك. لا يغير الرصيد ولا يعيد بناء التاريخ السابق |
| OPENING_BALANCE / MANUAL_GRANT / CORRECTION | الأثر الفعلي لطلب افتتاحية أو منح/تصحيح يدوي، مع مفتاح الطلب وسبب المستخدم أو وصف العملية |
| ACCRUAL | الزيادة الفعلية نحو هدف الاستحقاق، أو المكتسب المحسوب عند أول موافقة إذا لم يوجد صف رصيد |
| USAGE | زيادة المستخدم عند اعتماد طلب، بمصدر LEAVE_REQUEST ومعرف الطلب |
| CLOSE_OUT | أثر إقفال المصدر؛ يبين TransferredDays وExpiredDays من لقطة الإقفال |
| CARRY_FORWARD | الزيادة في مرحّل الدورة التالية، بمصدر YEAR_CLOSE ومعرف الإقفال |
| REVERSAL | عكس دقيق لحركة الإقفال الأصلية، مع ReversesMovementId؛ يمنع عكس الحركة نفسها مرتين |
| LEGACY_REVERSAL | عكس إقفال نُشر قبل وجود الدفتر، باستخدام لقطة الإقفال المعروفة، دون اختراع معرف حركة أصلية غير موجودة |

حقول أيام الترحيل وصف للمصدر والهدف، وتظهر في حركتي الخروج والدخول. لا يُجمع TransferredDays عبر الجانبين لاحتساب رصيد جديد؛ استعمل الدلتا لإعادة تكوين الرصيد. أيام الانتهاء تسجل على المصدر، ويعكسها قيد العكس بالسالب.

جدول الدفتر لا يُملأ بحركات مفترضة عند تثبيته. لكل رصيد قديم تُنشأ OPENING_SNAPSHOT عند أول تغيير مسجل، ثم الحركة الجديدة في المعاملة نفسها. لذلك قد يعيد API صفراً من الحركات لرصيد محفوظ لم يُعدّل بعد. الاستيراد المنظم لتاريخ العملاء القديم يبقى LEV-16.

## الذرية والتكرار والعكس

- تُحفظ الحركة وتغير الرصيد في معاملة الكاتب نفسها، تحت أقفال الموظف والنوع وفق LEV-13. لا يجوز استدعاء مسجل الحركات خارج معاملة كتابة.
- OPERATION_KEY فريد داخل مخطط الشركة؛ BALANCE_ID + SEQUENCE_NO فريدان؛ REVERSES_MOVEMENT_ID فريد عند وجوده.
- يطابق المسجل حالة ما قبل التغيير مع آخر حركة محفوظة. اختلافهما يوقف الكتابة للمصالحة، بدلاً من إخفاء تغيير غير مسجل.
- تكرار هدف الاستحقاق بلا زيادة لا يضيف حركة أخرى. معرف الحركة مشتق من الموظف والنوع والدورة والقيمة المستهدفة. هذا لا يضيف مهمة تراكم مجدولة (LEV-11).
- نشر الإقفال أو عكسه مجدداً في الحالة نفسها يعيد حالته دون حركة إضافية. إعادة النشر بعد العكس تضيف دورة جديدة من الحركات؛ لا تعدل القديمة.
- يمنع عكس إقفال له حركات لاحقة فعالة أو دورة هدف مقفلة. بعد عكس الإقفال التابع وحركاته المرتبطة، يمكن عكس الأصل إذا تطابقت أرصدته ولقطته.
- EF يرفض تعديل/حذف حركة محفوظة. Trigger Oracle باسم TR_HR_LEAVE_MOVEMENT_IMM يرفض UPDATE وDELETE برمز ORA-20071. العكس دائماً INSERT مرتبط.
- أُصلح اسم bind parameter القديم `rowId` في أقفال الإقفال؛ Oracle يعامله كاسم ROWID المحجوز ويعيد ORA-01745. الاسم الآن `recordId`، وقد اجتاز دورة Post/Unpost الفعلية.

## عقد API الجديد

### تعديل الرصيد اليدوي

`POST /api/hr/leaves/balances/grant` يحتفظ بصلاحية `hr-leaves/edit` الحالية، ويحتاج الآن **idempotencyKey** من 1 إلى 200 حرف. يجب حفظ المفتاح نفسه لإعادة محاولة الطلب نفسه، واستخدام مفتاح جديد للعملية الجديدة. Days بدقة أربع منازل كحد أقصى.

```json
{
  "employeeCode": "EMP001",
  "leaveTypeCode": "ANNUAL",
  "yearNo": 2026,
  "days": 2,
  "adjustmentType": "CORRECTION",
  "reason": "تصحيح رصيد موثق",
  "idempotencyKey": "6c538ddc-a54b-42ed-821c-833ec041fc7f"
}
```

إعادة المفتاح مع المحتوى نفسه تعيد القيم الأصلية للنتيجة دون كتابة، حتى إن أُقفلت الدورة لاحقاً. المفتاح نفسه مع مبلغ أو موظف أو نوع أو سنة أو سبب مختلف يرفض الطلب. تُسوّى الكسور العددية المتكافئة، والمسافات الخارجية للسبب ونوع التعديل. الطلب بلا مفتاح يرفض؛ يجب مزامنة العميل قبل نشر هذا الكود.

تسجيل حركة يثبت أثر المسار الحالي؛ لا يضيف سير Draft/Post/Unpost جديداً للتعديلات اليدوية. ضبط سبب التعديل وحدوده واعتماده منفصل في LEV-19.

### قراءة الحركات

`GET /api/hr/leaves/balances/{employeeCode}/movements?leaveTypeCode=ANNUAL&cycleStart=2026-01-01&page=1&size=50`

- الصلاحية: hr-leaves/view مع الخدمة الذاتية بنفس آلية تحديد الموظف والفروع الحالية.
- page: من 1 إلى 1000000؛ size: من 1 إلى 200. الرد Items وTotalCount وPageIndex وPageSize داخل ApiResponse.
- Items تعرض المصدر والسبب والفاعل والتوقيت، والدلتا والقيم بعدها والمتاح وأيام الانتهاء/الترحيل ورابط العكس. الأحدث أولاً. سجل الرصيد مرتبط بالمخطط الحالي ويخضع لفلتر الموظف في EF.
- لا توجد واجهة لتعديل أو حذف حركة. إلغاء طلب وإرجاع استخدامه ما زال LEV-14، ولم يُضف ضمن هذه الحزمة.

## تطبيق DEV_TEMPLATE والأدلة

- نسخة Data Pump محلية قبل التثبيت: `artifacts/hr-audit/backups/20261105090027/dev_template_20261105090027.dmp` بحجم 8,257,536 بايت. تصدير COMPLETED وسجل بلا ORA، وبصمة الملف المحلي طابقت manifest.json. الملفات مستثناة من Git. الاستعادة التجريبية ما زالت OPS-11.
- `--install-leave-ledger` أنشأ HR_LEAVE_MOVEMENT وقيوده، ثم ثُبت trigger عدم التعديل. لا يُشغّل تلقائياً ولا يضيف أدواراً أو منح صلاحيات. تكراره لا ينسخ بيانات؛ يعيد تثبيت الحماية ويفحص mapping.
- ترتيب النشر: نسخة احتياطية، تثبيت الجدول والحماية في المخطط المستهدف، فحص mapped SELECT، مزامنة عقد المفتاح مع العميل، ثم نشر التطبيق. يجب تنسيق انتقال كل الكتابات إلى الإصدار المسجل للدفتر؛ أي كتابة قديمة مباشرة بعد بدء الدفتر ستؤدي إلى اختلاف يحتاج مصالحة.
- المخطط الحالي: 38 كيان EF مقابل 63 جدول HR. كل أعمدة الدفتر mapped موجودة وقَبِل Oracle SELECT. لم تتغير أرصدة العمل القديمة؛ بعد rollback الاختبارات يوجد **0 صف** في جدول الحركات.
