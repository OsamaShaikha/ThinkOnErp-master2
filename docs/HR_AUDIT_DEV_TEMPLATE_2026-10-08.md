# فحص HR وربط الموظفين بالحسابات — DEV_TEMPLATE

> هذا تقرير الفحص الأول قبل الموافقة على الإصلاحات. النتائج اللاحقة موثقة في [تقرير الإصلاح](HR_REPAIR_DEV_TEMPLATE_2026-10-08.md).

التاريخ: 8 أكتوبر 2026، بتوقيت عمّان.

**النتيجة: تم تنفيذ الربط المطلوب في الكود وقاعدة البيانات. HR يحتاج إصلاحات إضافية قبل الاعتماد عليه كدورة تشغيل متكاملة. لم تُصلح المشاكل الإضافية احتراماً لطلب عرضها أولاً.**

## ما تم تنفيذه

- إضافة `DEV_TEMPLATE.HR_EMPLOYEE.USER_ID` كحقل رقمي اختياري.
- مرجع إلى `DEV_TEMPLATE.SYS_USERS."Id"` باسم `FK_HR_EMPLOYEE_USER`، دون حذف متسلسل.
- قيد تفرد `UX_HR_EMPLOYEE_USER_ID` يمنع ربط الحساب بأكثر من موظف، ويسمح بموظفين دون حساب.
- التحقق الفعلي من أن القيدين `ENABLED` و`VALIDATED` وأن قاعدة الحذف `NO ACTION`.
- إضافة ربط وفك ربط عبر API للمسؤول فقط، مع التحقق من نشاط الموظف والحساب، وجود الحساب داخل مخطط الشركة، وصلاحية الحساب لفرع الموظف.
- منع تغيير فرع الموظف المرتبط إلى فرع لا يملك حسابه الوصول إليه، عبر التعديل العادي والاستيراد من Excel.
- إضافة `UserId` إلى نتائج قائمة الموظفين وتفاصيل الموظف، وحماية بيانات حساب المستخدم من الظهور عند تسلسل الموظف إلى JSON.
- إضافة lookup لحساب المستخدم الحالي باستخدام معرفه من التوكن.
- إنشاء سكربت خاص بـDEV_TEMPLATE وترحيل EF يقتصر على هذا الربط. تم استبعاد الفروقات القديمة غير المتعلقة بالطلب من الترحيل الجديد.

لم يُربط أي موظف بحساب تلقائياً؛ عدد الروابط الفعلي بعد التنفيذ: **0**. لم تُنشأ حسابات أو تُغيّر كلمات مرور أو رواتب. تعديل الكود لم يُنشر إلى خادم التشغيل، ولم تتغير واجهة HTML الحالية.

## استخدام الربط

المسؤول يستعمل، مع توكن صحيح وسياق الشركة المعتاد:

```http
PUT /api/hr/employees/EMP001/user-link
Content-Type: application/json

{"userId": 12}
```

المثال توضيحي؛ اختر معرف الحساب الصحيح للموظف. لفك الربط أرسل `{"userId": null}` إلى نفس المسار. المعرف ليس كلمة مرور ولا يعطي صلاحيات إضافية.

```http
GET /api/hr/employees/me/user-link
```

يعيد رابط الموظف للحساب الحالي أو 404 إذا كان غير مرتبط. إنشاء الحساب يظل ضمن إدارة المستخدمين الحالية. خدمات «إجازاتي» و«حضوري» تحتاج لاحقاً تطبيق الملكية والصلاحيات على عمليات HR الحالية؛ هذا lookup لا يجعلها آمنة تلقائياً.

## نطاق الفحص والأدلة

- مراجعة مخطط Oracle الفعلي: **58 جدول HR**، ومقارنة **33 جدولاً ممثلاً في نموذج EF** بأعمدته المتوقعة.
- قبول Oracle لعبارات SELECT الخاصة بالأعمدة الممثلة في **30 جدولاً** دون قراءة بيانات الأشخاص. الجداول الثلاثة الأخرى لديها أعمدة ناقصة.
- قراءة أعداد الصفوف للتحقق من اختلاف جداول البيانات القديمة والجداول التي يقرأها التطبيق.
- مراجعة الربط، إدارة الموظفين، الرواتب، السياسات، السلف والقروض، الإجازات، الحضور والتصحيحات، التقويم، الترحيل المحاسبي والتصدير البنكي ومسارات الصلاحيات.
- نجاح **95 اختباراً** في مشروع `ThinkOnErp.HR.Tests`: يتضمن **24 اختباراً للفواتير وPOS** و**71 اختباراً متعلقة بـHR والربط**.
- نجاح **6 اختبارات** مستقلة لنقاط API الجديدة: سياسة المسؤول، معرف الحساب الحالي، رفض معرف غير صالح، وحساب غير مرتبط.
- بناء مشروع API ناجح. مشروع اختبارات API العام لا يُبنى بسبب أخطاء سابقة في اختبارات الشركات والعملات.
- ثلاثة اختبارات توصيف أعادت إنتاج مشاكل تواريخ الرواتب، تجاوز رصيد الإجازة عند الاعتماد، وتعديل رصيد القرض أثناء الحساب المبدئي. نجاح هذه الاختبارات يؤكد وجود السلوك الخاطئ الحالي، ولا يعني إصلاحه.

الفحص لا يتضمن نشر التطبيق أو تنفيذ معاملات رواتب واعتمادات على البيانات الفعلية أو تحويلات بنكية، ولا يمثل اعتماداً قانونياً لصحة قواعد الضريبة والضمان. كثير من جداول التشغيل فارغة، لذلك لا يوجد دليل كافٍ على دورة إنتاج كاملة. جرى فحص الجداول الإضافية كجرد قاعدة بيانات، وليس كوظائف API مكتملة.

## ترتيب الإصلاح المقترح بعد موافقتك على النطاق

1. صلاحيات HR والملكية، وأعمدة الحضور الناقصة.
2. توحيد مصدر الرواتب والورديات ومطابقة البيانات القديمة.
3. فصل حساب القروض عن التسوية، وسياسة الاعتماد، والإعفاءات وأسس المكونات.
4. دمج الإضافي، وحماية رصيد الإجازة وتواريخ الرواتب، وضبط الترحيل المحاسبي.
5. دورة إنهاء الخدمة، وإصلاح الاختبارات العامة، ثم دورة قبول كاملة عبر API ببيانات اختبار مخصصة.
