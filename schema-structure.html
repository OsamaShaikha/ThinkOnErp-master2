✎

🔐

✎

⚙

New Features & Schema Changes

Detailed breakdown of each structural change introduced in v2.

👥 User ↔ Branch Multi-Assignment
A user must be assigned to at least 1 branch. Can be assigned to multiple branches. One branch is marked as primary.
-- NEW TABLE: SYS_USER_BRANCHES (Tenant Schema) CREATE TABLE SYS_USER_BRANCHES ( "Id" NUMBER(19) GENERATED ALWAYS AS IDENTITY PRIMARY KEY, "USER_ID" NUMBER(19) NOT NULL, -- FK → SYS_USERS "BRANCH_ID" NUMBER(19) NOT NULL, -- FK → SYS_BRANCH "IS_PRIMARY" NUMBER(1) DEFAULT 0, -- One branch is primary "ASSIGNED_BY" NUMBER(19), -- Who assigned this "ASSIGNED_AT" DATE DEFAULT SYSDATE, CONSTRAINT UQ_USER_BRANCH UNIQUE ("USER_ID", "BRANCH_ID") ); -- SYS_USERS: Remove BranchId column ALTER TABLE SYS_USERS DROP COLUMN "BRANCH_ID";
🔢 Branch Users Limit
Each branch has a maximum number of users. The API validates this limit when assigning users to a branch via SYS_USER_BRANCHES.
-- MODIFIED: SYS_BRANCH (Tenant Schema) ALTER TABLE SYS_BRANCH ADD ( "USERS_LIMIT" NUMBER(10) DEFAULT 0 -- 0 = unlimited ); -- API validation logic: -- SELECT COUNT(*) FROM SYS_USER_BRANCHES -- WHERE BRANCH_ID = :branchId; -- IF count >= branch.USERS_LIMIT AND USERS_LIMIT > 0 -- THEN THROW "Branch user limit reached";
🔐 SuperAdmin PIN Confirmation
Edit and Delete actions by SuperAdmin require a PIN code. The PIN is hashed and stored in SYS_SUPER_ADMIN. Each mutation API call includes a pinCode field.
-- MODIFIED: SYS_SUPER_ADMIN (SuperAdmin Schema) ALTER TABLE SYS_SUPER_ADMIN ADD ( "PIN_HASH" VARCHAR2(256) -- Hashed PIN for edit/delete ); -- API request example: -- PUT /api/superadmin/branches/5 -- { -- "branchNameEn": "New Name", -- "pinCode": "1234" ← verified server-side -- } -- Server-side: -- var admin = await _db.SysSuperAdmins.FindAsync(adminId); -- if (!VerifyHash(request.PinCode, admin.PinHash)) -- return Unauthorized("Invalid PIN");
📄 SYS_DOCUMENT in Both Schemas
Platform-level documents (contracts, templates) live in SuperAdmin schema. Company-level documents (invoices, reports) live in tenant schema. Same table structure, different data.
-- SuperAdmin Schema: SYS_DOCUMENT -- Platform templates, license files, global docs -- Managed by SuperAdmin only -- Tenant Schema: SYS_DOCUMENT -- Company invoices, reports, attachments -- Managed by company admin and users -- Both use the same entity: SysDocument -- The schema determines which data is accessed
📋 Audit Log Access Rules
Audit logs live in tenant schema for data isolation. SuperAdmin has full access via schema switch. Tenant users can only view — no edit, no delete.
-- SuperAdmin access flow: -- 1. Query SYS_COMPANY for target schema -- 2. ALTER SESSION SET CURRENT_SCHEMA = "TENANT_X" -- 3. Full CRUD on SYS_AUDIT_LOG -- Tenant user access: -- Can only call GET endpoints -- POST/PUT/DELETE blocked at API level -- [Authorize(Policy = "SuperAdminOnly")] -- on all mutation endpoints
🔑 Permission Delegation Flow
SuperAdmin grants systems/screens/features to a branch. Company Admin can only assign roles and user permissions within what SuperAdmin granted. Cannot exceed branch-level permissions.
-- Step 1: SuperAdmin grants HR system to Branch 1 -- INSERT INTO SYS_BRANCH_SYSTEMS -- (BRANCH_ID=1, SYSTEM_ID=3, IS_ALLOWED=1) -- Step 2: Company Admin creates a role with HR access -- INSERT INTO SYS_ROLE_SCREEN_PERMISSIONS -- (ROLE_ID=5, SCREEN_ID=12, CAN_VIEW=1, CAN_INSERT=1) -- ⚠️ API validates: Screen 12 must belong to -- a system granted to the user's branch -- Step 3: Company Admin assigns role to user -- INSERT INTO SYS_USERS_ROLES (USER_ID=8, ROLE_ID=5)

Permission Hierarchy Flow

SuperAdmin grants access to branches → Company Admin assigns roles/permissions to users within what was granted.

⚠️
Key Rule: Company Admin can never grant permissions that SuperAdmin hasn't first granted to the branch. The API validates every role/user permission against SYS_BRANCH_SYSTEMS, SYS_BRANCH_SCREENS, and SYS_BRANCH_FEATURES.
Level 1 — System Licensing
Is the System Licensed for this Company?
SYS_COMPANY ↔ SYS_SYSTEM
SuperAdmin manages
Licensed ✓
Level 2 — Branch System Access
Is the System Enabled for this Branch?
SYS_BRANCH_SYSTEMS
SuperAdmin grants
Allowed ✓
Level 3 — Branch Screen Access
Is the Screen Enabled for this Branch?
SYS_BRANCH_SCREENS + SYS_BRANCH_FEATURES
SuperAdmin grants
Allowed ✓
Level 4 — Role Permissions
Does the User's Role Have Access?
SYS_ROLE_SCREEN_PERMISSIONS
Company Admin assigns (within branch grants)
Has Permission ✓
Level 5 — User Override
User-Level Permission Override?
SYS_USER_SCREEN_PERMISSIONS
Company Admin assigns (within branch grants)
✅ ACCESS GRANTED
ℹ️
Multi-Branch Users: When a user belongs to multiple branches, permissions are evaluated per-branch. The user sees the union of permissions across all assigned branches.

Tenant Provisioning Workflow

What happens when SuperAdmin creates a new company. Updated with new tables and seed data.

💡
SYS_CODE, SYS_SETTINGS, and ticket lookup tables are seeded from global defaults during provisioning. Only SuperAdmin can modify them afterward.
Step 1 — SuperAdmin Schema
Register the Company
INSERT INTO SYS_COMPANY (COMPANY_CODE, LEGAL_NAME, COMPANY_SCHEMA, CREATED_BY_SUPER_ADMIN_ID) VALUES ('ACME001', 'Acme Corporation', 'TENANT_ACME', 1);
Step 2 — Oracle
Create Tenant Schema + Grant Access
CREATE USER "TENANT_ACME" IDENTIFIED BY "***"; GRANT CONNECT, RESOURCE TO "TENANT_ACME"; -- Grant master user access for schema switching GRANT SELECT, INSERT, UPDATE, DELETE ON all 28 tables TO THINKON_ERP;
Step 3 — Tenant Schema
Run EF Core Migrations (creates all 28 tenant tables)
ALTER SESSION SET CURRENT_SCHEMA = "TENANT_ACME"; -- EF Core creates all 28 tables including: -- NEW: SYS_USER_BRANCHES (User ↔ Branch junction) -- MODIFIED: SYS_BRANCH (+ USERS_LIMIT column) -- MODIFIED: SYS_USERS (BranchId removed)
Step 4 — Tenant Schema
Seed Default Data
INSERT INTO SYS_BRANCH (NAME, IS_HEAD_BRANCH, USERS_LIMIT) VALUES ('Head Office', 1, 50); INSERT INTO SYS_ROLE (ROLE_NAME) VALUES ('Admin'), ('User'), ('Viewer'); INSERT INTO SYS_TICKET_TYPE (...) -- copy global defaults INSERT INTO SYS_TICKET_STATUS (...) -- copy global defaults INSERT INTO SYS_TICKET_PRIORITY (...) -- copy global defaults INSERT INTO SYS_CODE (...) -- copy global defaults (SA-only access) INSERT INTO SYS_SETTINGS (...) -- copy global defaults (SA-only access) INSERT INTO SYS_RETENTION_POLICIES (...) -- copy global defaults
Step 5 — SuperAdmin Schema
Link Default Branch + Grant Permissions
-- Update company with default branch UPDATE SYS_COMPANY SET DEFAULT_BRANCH_ID = :newBranchId WHERE COMPANY_CODE = 'ACME001'; -- SuperAdmin grants initial system access to the head branch -- via SYS_BRANCH_SYSTEMS, SYS_BRANCH_SCREENS, SYS_BRANCH_FEATURES
Step 6 — Create Admin User
Create Company Admin + Assign to Branch
-- Create the first admin user INSERT INTO SYS_USERS (USER_NAME, IS_ADMIN) VALUES ('admin@acme', 1); -- Assign admin to head office branch (required!) INSERT INTO SYS_USER_BRANCHES (USER_ID, BRANCH_ID, IS_PRIMARY) VALUES (:userId, :branchId, 1); -- Assign admin role INSERT INTO SYS_USERS_ROLES (USER_ID, ROLE_ID) VALUES (:userId, :adminRoleId);
