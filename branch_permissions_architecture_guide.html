🛡️ المعمارية والأمان • ThinkOnErp Multi-Tenant

دليل إدارة صلاحيات الأنظمة وحجب الشاشات والميزات للفروع

شرح تفصيلي تقني ومعماري لكيفية قيام السوبر أدمن (Super Admin) بتعيين الأنظمة للفروع، وحجب شاشة كاملة أو ميزة/زر معين، والتحقق الهرمي الصارم لعدم تجاوز الصلاحيات الممنوحة من قبل أدمن الشركة أو المستخدمين.

المستوى 1 • السوبر أدمن
تخصيص الأنظمة (Branch Systems)
تحديد الأنظمة الكلية المتاحة للفرع (المحاسبة، HR، التذاكر...).
المستوى 2 • السوبر أدمن
حجب الشاشات (Branch Screen Revocation)
تقييد أو حجب شاشة كاملة عن الفرع استثناءً من النظام.
المستوى 3 • السوبر أدمن
حجب الميزات (Branch Feature Revocation)
حجب زر أو ميزة محددة داخل شاشة مجهزة للفرع (مثل حجب زر الحذف/التصدير).
المستوى 4 • أدمن الشركة
صلاحيات الأدوار والمستخدمين (Roles & Users)
توزيع الصلاحيات على المستخدمين والأدوار ضمن نطاق ما سمح به السوبر أدمن فقط.
🗄️

1. الهيكلية والمحتوى في قاعدة البيانات (Database Schema)

يعتمد النظام على فصل كامل بين الكتالوج المركزي للأنظمة والميزات، وبين التعيين والقيود (Revocations) الخاصة بكل فرع:

الجدول (Entity) المستوى / النطاق الوصف التقني والوظيفة
SYS_SYSTEM الكتالوج المركزي (Master) يحتوي على كافة الأنظمة البرمجية المتاحة في السحابة (مثال: `ACC`, `HR`, `INVENTORY`, `TICKETS`).
SYS_SCREEN الكتالوج المركزي (Master) الشاشات التابعة للأنظمة (مثال: شاشة إضافة فاتورة `ACC_INV_CREATE` تابعة لنظام `ACC`).
SYS_FEATURE الكتالوج المركزي (Master) الميزات والأزرار العملية داخل الشاشات (مثال: `CREATE`, `UPDATE`, `DELETE`, `PRINT`, `EXPORT`).
SYS_BRANCH_SYSTEMS تخصيص الفرع (Branch Provisioning) ربط الأنظمة المسموح بها لفرع معين. الشاشات التابعة لهذه الأنظمة تصبح مرشحة للظهور للفرع.
SYS_BRANCH_SCREENS قيود الفرع (Branch Revocations) يخزن الشاشات المحجوبة (Revoked) عن فرع معين استثناءً بواسطة السوبر أدمن.
SYS_BRANCH_FEATURES قيود الفرع (Branch Revocations) يخزن الميزات/الأزرار المحجوبة (Revoked Features) عن شاشة معينة في فرع محدد.
SYS_ROLE_SCREEN_PERMISSIONS صلاحيات الفرع (Tenant Roles) صلاحيات الأدوار الممنوحة من قبل مدير الشركة داخل الفرع.
SYS_USER_SCREEN_PERMISSIONS صلاحيات الفرع (Tenant Users) تجاوزات الصلاحيات المباشرة لمستخدم معين داخل الفرع (User Overrides).

2. كيف يقوم السوبر أدمن بإدارة وإعطاء الصلاحيات وحجبها للفرع؟

يتم تنفيذ عمليات السوبر أدمن عبر مجموعة الـ APIs المخصصة للتحكم بالوصول على مسار контроллер BranchAccessController:

PUT /api/branches/{branchId}/access/systems
أولاً: تخصيص الأنظمة للفرع (Assign Systems to Branch)
يقوم السوبر أدمن بتمرير مصفوفة من `systemIds` لربط الأنظمة المتاحة للفرع.
{ "systemIds": [1, 2, 5] }
POST /api/branches/{branchId}/access/screens/{screenId}/revoke
ثانياً: حجب شاشة كاملة عن الفرع (Revoke Screen from Branch)
إذا كان النظام (مثلاً نظام المحاسبة ID=1) متاحاً للفرع، ولكن السوبر أدمن يريد حجب شاشة القيود اليومية (ID=105) عن هذا الفرع تحديداً:
// إرسال POST لهذا المسار ينشئ قيد حجب في جدول SYS_BRANCH_SCREENS HTTP 200 OK -> { "success": true, "message": "Screen revoked successfully" }
DELETE /api/branches/{branchId}/access/screens/{screenId}/revoke
إلغاء حجب شاشة وإعادتها للفرع (Re-allow Screen)
عند رغبة السوبر أدمن في فك الحجب وإتاحة الشاشة للفرع مجدداً.
POST /api/branches/{branchId}/access/screens/{screenId}/features/{featureId}/revoke
ثالثاً: حجب ميزة أو زر معين داخل شاشة للفرع (Revoke Specific Feature)
إذا كانت الشاشة متمثلة بشاشة الفواتير (ScreenId=10), وأراد السوبر أدمن حجب زر "حذف فاتورة" (FeatureId=4 - DELETE) عن هذا الفرع:
// ينشئ قيد حجب في جدول SYS_BRANCH_FEATURES HTTP 200 OK -> { "success": true, "message": "Feature revoked successfully" }
DELETE /api/branches/{branchId}/access/screens/{screenId}/features/{featureId}/revoke
إلغاء حجب الميزة وإعادة إتاحتها للفرع (Re-allow Feature)
لحذف قيد الحجب وإرجاع إمكانية منح الميزة لأدوار المستخدمين.

3. الحماية والتحقق الهرمي الصارم (Strict Scope Validation)

عندما يحاول أدمن الشركة (Company Admin) إعطاء صلاحيات لأحد الأدوار أو المستخدمين في الفرع عبر CompanyPermissionsController:

خطوة 1

استلام طلب تعديل صلاحيات الدور/المستخدم

يتلقى النظام طلب إعطاء صلاحيات عبر `PUT /api/branches/{branchId}/permissions/roles/{roleId}`.

خطوة 2

فحص النطاق المحجوب (ValidateBranchPermissionsScopeAsync)

يفحص النظام هل الشاشات والميزات المطلوبة تنتمي لأنظمة مخصصة للفرع أولاً، وهل هي غير محجوبة في `SYS_BRANCH_SCREENS` أو `SYS_BRANCH_FEATURES`.

خطوة 3

الرفض الفوري عند اكتشاف محاولة تجاوز قيد السوبر أدمن

إذا حاول أدمن الشركة إعطاء ميزة أو شاشة قام السوبر أدمن بحجبها على مستوى الفرع، يتم إرجاع استجابة رفض حاسمة برمز `400 Bad Request`.

⚠️
مثال لرسالة الرفض عند محاولة تجاوز حجب السوبر أدمن:

"Feature ID 4 (DELETE) on screen 'Invoices' is revoked for this branch by SuperAdmin."

⚙️

4. خوارزمية احتساب الصلاحيات عند تشغيل النظام (Runtime Evaluation)

عندما يطلب مستخدم عادي شاشاته المتاحة عبر كود التنفيذ في PermissionsController.GetMyScreens() أو فحص صلاحية زر عبر PermissionService.CanAccessByCodeAsync، يتم الاستعلام وفق التسلسل التالي:

// خوارزمية تقييم الصلاحيات في PermissionService / PermissionsController: 1. هل المستخدم SuperAdmin؟ ---> نعم: يمنح صلاحية كاملة (Master Access) مع التزام سياق الشركة (X-Company-Id). 2. هل النظام التابع للشاشة مخصص للفرع في (SYS_BRANCH_SYSTEMS)؟ ---> لا: يُحجب فوراً. 3. هل الشاشة مضافة في قائمة حجب الفرع (SYS_BRANCH_SCREENS)؟ ---> نعم: تُلغى الشاشة بالكامل ويُمنع الوصول إليها. 4. هل الميزة/الزر مضاف في قائمة حجب ميزات الفرع (SYS_BRANCH_FEATURES)؟ ---> نعم: تُحجب الميزة ولا تظهر للمستخدم أبداً. 5. فحص تجاوزات المستخدم الخاص (SYS_USER_SCREEN_PERMISSIONS): - إذا وجد قيد حجب صريح (IsGranted = 0) ---> تُحجب الميزة. - إذا وجد قيد منح صريح (IsGranted = 1) ---> تُمنح الميزة. 6. فحص صلاحيات دور المستخدم (SYS_ROLE_SCREEN_PERMISSIONS): - إذا كان الدور يملك منح صريح (IsGranted = 1) ولم تُحجب من الفرع ---> تُمنح الميزة.
✨
النتيجة التكاملية لسلامة النظام:

تضمن هذه المعمارية التحكم الكامل والسيطرة المطلقة للسوبر أدمن على الفروع، مع مرونة تامة لمدراء الشركات لتوزيع الصلاحيات اليومية في حدود السقف المحدد لكل فرع.
