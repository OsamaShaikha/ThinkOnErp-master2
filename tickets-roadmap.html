ThinkOnERP Tickets Roadmap

A practical guide for using the ticket system from SuperAdmin and tenant branch dashboards: what each role does, which API routes are used, and how to test safely.
1. Overview 2. Roles and scope 3. Ticket lifecycle 4. API route map 5. SuperAdmin usage 6. Tenant branch usage 7. Test plan 8. Troubleshooting 9. Recommended next steps

1. Overview

The ticket system is the support/request module in ThinkOnERP. A ticket belongs to one company and one branch, is opened by a requester, may be assigned to a support user, and moves through statuses until resolution.

CompanyThe tenant/account that owns the ticket data.
BranchThe operational unit where the issue/request happened.
SLAExpected resolution timing based on priority/type rules.
SuperAdmin is for system-wide visibility and reports. Tenant branch users are for daily branch operations: create, view, comment, and move their own branch tickets.

2. Roles and scope

ActorLogin/API surfaceExpected ticket scopeMain actions
SuperAdmin POST /api/auth/superadmin/login Platform-wide. Can inspect/filter all companies and branches. System reports, SLA overview, ticket assignment, status operations, admin testing.
Company Admin POST /api/Auth/login with company code Company tenant schema. Should not see other companies. Manage company/branch ticket activity, create tickets, status/comment workflows.
Branch User POST /api/Auth/login Branch-level operational view, based on token/permissions. Create requests, check own/branch tickets, add comments, follow status.
Tenant isolation depends on the JWT company claims and SchemaRoutingMiddleware, which sets Oracle CURRENT_SCHEMA for authenticated tenant requests.

3. Ticket lifecycle

1
Create
A branch user/company admin creates a ticket with title, description, company, branch, requester, type, priority, and optional category.
2
Open
The system sets the initial status, calculates expected resolution from SLA rules, and stores the ticket.
3
Assign
An admin or SuperAdmin assigns the ticket to a support user. Assignment may move status to in progress.
4
Comment / attach
Users add discussion notes and attachments. Internal comments are admin-only context.
5
Status update
The ticket moves through allowed status transitions. Invalid transitions should return validation errors.
6
Resolve and report
Resolution date and SLA compliance are used in reports: volume, SLA compliance, and workload.

5. How SuperAdmin should use tickets

Use case

SuperAdmin monitors support health across the platform. They can filter by company/branch, inspect SLA risk, run reports, and make admin-level assignments or status changes.

Open superadmin-system-tickets-dashboard.html, login as SuperAdmin or paste a SuperAdmin JWT, then start with read-only tests.

Safe order

  1. Run public health.
  2. Login SuperAdmin.
  3. Load ticket types.
  4. Load tickets with small page size, for example 5 or 10.
  5. Open one ticket detail.
  6. Run reports.
  7. Only then test assign/status/comment on a test ticket.
Assignment, status update, comments, delete, and create operations write to the database and audit logs. Do not use those buttons on production records unless you really mean it.

6. How tenant branches should use tickets

Company login

Tenant users login with companyCode, username, and password. The token carries company and schema information so the request runs inside the tenant schema. 

{
  "companyCode": "TECH01",
  "userName": "tech_admin",
  "password": "..."
}

Branch flow

  1. Login tenant user.
  2. Load branches visible to that user.
  3. Select branch.
  4. List branch tickets.
  5. Create a test ticket if needed.
  6. Open detail, add comments, update status.
Expected behavior: a company admin sees only their company branches; branch users should be scoped to their branch/permissions. If a tenant user sees another company’s tickets, that is a tenant isolation bug.

8. Troubleshooting

SymptomLikely causeWhat to do
Failed to fetch API is not running, wrong API base URL, or CORS/network issue. Start API on http://localhost:5000, then test /api/AuditHealth/status.
401 Unauthorized Missing/expired token or wrong login type. Login again. Use SuperAdmin login for SuperAdmin page and company login for branch page.
403 Forbidden User authenticated but lacks AdminOnly permission. Use SuperAdmin/company admin for reports, assignment, or delete operations.
Ticket list timeout Query is heavy, joins are slow, Oracle session is busy, or ticket table lacks needed indexes. Test with pageSize=5, filter by branch/company, then inspect repository query and database plan.
Wrong branch/company data Tenant schema or filter is wrong. Check JWT claims: companyId, branchId, companySchema.
Invalid status transition Workflow rules reject the move. Check current status ID and allowed transition logic before updating.

9. Recommended next steps

A
Seed clean test ticket data
Create a small set of tickets for TECH01 branches with known status/priority/type IDs.
B
Fix or profile ticket list timeout
If GET /api/tickets times out, profile TicketRepository and the Oracle query generated by EF.
C
Enforce tenant/branch scope
Confirm company admins see only company branches/tickets and branch users see only allowed branch tickets.
D
Add a “safe test mode”
Use test records with titles like API TEST so destructive actions never touch real tickets.
Never use the mutation buttons on real production tickets until you have confirmed token scope, branch scope, and test data.
