Executive summary

ThinkOnERP is a substantial multi-tenant ERP backend with platform administration, tenant operations, branch provisioning, support ticketing, document storage, and a particularly ambitious audit and compliance system.

The production application currently compiles, and its architecture has clear separation between API, application, domain, and infrastructure concerns. The most important weakness is engineering drift: the full solution fails because much of the test suite no longer matches the production interfaces. Several production-hardening concerns also deserve attention before the system is treated as reliably deployable.

No source files were modified during the assessment. Existing uncommitted permission-system work was preserved.

Priority findings

P0

Test suite no longer compiles

The repository presents broad test coverage, but the full solution currently produces 323 errors caused by changed constructors, deleted members, namespace collisions, stale mocks, and incompatible package versions. Regression confidence is therefore much lower than the test-file count suggests.

P0

Tenant refresh-token flow appears inconsistent

Company login saves refresh tokens into the tenant schema. The refresh endpoint uses the central AuthRepository before an authenticated JWT can provide schema context. This may prevent tenant token refresh or cause it to query the wrong schema.

P0

Schema identifier is interpolated into raw SQL

SchemaRoutingMiddleware constructs ALTER SESSION SET CURRENT_SCHEMA using a JWT claim. Signed claims reduce exposure, but the schema should still be validated against a strict Oracle identifier pattern and an authoritative company record.

P1

Application startup mutates databases and tenant schemas

Startup seeds data, creates tenant schemas, seeds a default administrator, and upgrades existing tenants. This increases startup time, complicates horizontal deployment, and can cause concurrency or privilege failures.

P1

Production exposure defaults are broad

Swagger is always enabled and CORS permits every origin, method, and header. These settings should be environment-specific and driven by an explicit allowlist.

P1

Environment files are tracked

.env.production and .env.port5001 are committed. Any secrets ever stored in these files should be rotated and moved to deployment secret management.

P1

Advertised functionality includes unfinished paths

Several archival methods, cloud key providers, filesystem external storage, PDF/Excel exports, persistent alert rules, and holiday-calendar behavior remain TODOs or throw NotImplementedException.

P2

Documentation volume obscures the source of truth

The repository contains many implementation summaries, fix reports, deployment variants, and historical notes. Useful knowledge exists, but developers must distinguish current operational documentation from archived implementation history.

Recommended roadmap

Phase 1 — Restore trust

  1. Create a clean CI build for production projects.
  2. Classify tests as current, obsolete, integration-only, or performance-only.
  3. Align package versions and repair the smallest critical test suite first.
  4. Add smoke tests for login, refresh, schema routing, and permission checks.

Phase 2 — Secure tenancy

  1. Redesign company refresh-token resolution around company code/schema identity.
  2. Validate and allowlist tenant schema identifiers.
  3. Test Oracle session reuse and schema reset behavior.
  4. Verify every tenant endpoint uses the intended schema.

Phase 3 — Production hardening

  1. Move schema provisioning and upgrades into explicit jobs.
  2. Restrict Swagger and CORS by environment.
  3. Remove tracked secrets and rotate exposed credentials.
  4. Upgrade vulnerable and incompatible dependencies.

Phase 4 — Simplify ownership

  1. Publish one authoritative architecture document.
  2. Archive historical implementation summaries.
  3. Consolidate deployment scripts into one supported path.
  4. Track unfinished features explicitly instead of leaving runtime stubs.

Overall assessment

ThinkOnERP has strong scope, thoughtful operational ambitions, and a recognizable architecture. Its main challenge is not a lack of features—it is converting a fast-moving, documentation-heavy codebase into a system with dependable tests, controlled tenant boundaries, and one clearly supported production path.

The best next investment is stabilization rather than expansion. A reliable test baseline and a hardened tenancy/authentication flow will create far more leverage for every feature added afterward.
