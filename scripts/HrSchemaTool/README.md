# DEV_TEMPLATE HR repair utility

The repair also adds `HR_PRORATION_POLICY.SALARY_SEGMENT_ALLOCATION` with the legacy-safe default `UNCONFIGURED`. For salary transitions under `FIXED_30`, each company must explicitly select `CALENDAR_WEIGHTED` or `WORKING_WEIGHTED` through its proration policy. Apply this column before deploying the updated model; the utility is not executed automatically.

Payroll cancellation metadata (`CANCELLED_BY`, `CANCELLATION_DATE`, `CANCELLATION_REASON`) is added as nullable columns on `HR_PAYROLL_RUN`. Existing runs are not cancelled or rewritten by the repair.

Bank-payment snapshot columns (`CURRENCY_CODE`, `BENEFICIARY_NAME`, `BENEFICIARY_NATIONAL_ID`) are added as nullable columns on `HR_PAYROLL_RUN_LINE`. New calculations fill them from the salary and employee at calculation time. Existing approved runs need verified historical snapshot data before export; repair does not infer currency or beneficiary details from current employee records.

Write, repair, and verification modes in this utility are deliberately restricted to `DEV_TEMPLATE`. The optional `--schema-details-owner=SCHEMA` mode is read-only and exports Oracle data-dictionary metadata for one explicitly named HR schema; use it only with a separately approved isolated-schema connection, never `THINKONERP_DEV02` or a customer schema. It does not select row values or row counts. The tool reads the existing API Oracle configuration or the `ConnectionStrings__OracleDb` environment variable without printing connection details. Run from the repository root.

`--migration-history` is a standalone read-only inspection of `DEV_TEMPLATE.__EFMigrationsHistory`. If the tenant table is absent, it lists visible migration-history tables and may display the central `THINKON_ERP` history as a separate source; it never treats that central history as tenant state or writes a baseline.

`--apply-hr-tenant-migrations` applies only the fixed 37-migration offline SQL file at `artifacts/hr-audit/hr-tenant-migrations-37-offline.sql`, after checking the matching 37 migration IDs against source, a completed `DEV_TEMPLATE` backup's manifest/bytes/hash/log, the source script timestamp, current schema, and central EF-history column shape. If the tenant history table is absent, it creates the standard two-column table locally, then records each migration as the SQL script completes it. Oracle DDL commits independently; if the command stops, inspect the DEV_TEMPLATE history and error before resuming. This mode never targets other schemas or runs tests.

- `--preflight`: read-only column, constraint, row-count and mapped SELECT checks.
- `--install-hr-unicode-string-alignment`: after the Backend/migration batch is finalized, run alone on DEV_TEMPLATE to apply the same 16-column shadow conversion defined by tenant migration `20261114234500_AlignHrUnicodeStringColumns`. It runs every metadata, data round-trip, constraint, and index preflight before conversion DDL, then reruns the HR-wide bounded-string preflight. Take a fresh Data Pump backup immediately before applying it. No value is inferred or backfilled; unique constraints on `MIGRATION_KEY` and `SETTLEMENT_KEY` are preserved.
- `--write-hr-unicode-string-alignment-plan`: offline, no database connection; writes the exact ordered preflight and conversion SQL generated by the tenant migration to `artifacts/hr-audit/ops16-unicode-string-alignment.sql` for review before the DB batch.
- `--schema-details`: read-only HR types, precision, lengths, defaults, constraints, indexes, and trigger source/enabled/object status with compile errors; it also detects triggers owned by other schemas but attached to DEV_TEMPLATE HR tables. Includes aggregate balance migration checks, exact `COUNT(*)` totals for the fixed list of 23 HR tables without direct EF mappings, and static `ALL_DEPENDENCIES` references among DEV_TEMPLATE objects. Count queries return no row data and fail if a listed table is missing. Static-dependency results exclude dynamic SQL and objects owned by other schemas. Writes `artifacts/hr-audit/dev-template-schema-details.txt`; rejects combination with `--apply` or `--repair`. Build first with `dotnet build scripts/HrSchemaTool --no-restore -m:1`.
- `--schema-details-owner=SCHEMA`: standalone read-only metadata export for all visible `HR_%` tables under one validated Oracle owner. Starts an Oracle read-only transaction and records column definitions (including hidden/virtual flags), identity definitions, constraints and `SEARCH_CONDITION_VC`, indexes and function-based expressions, triggers/errors, cross-owner triggers attached to the schema's HR tables, and static dependencies visible in that schema. It does not read business rows or aggregate row counts, execute DDL/DML, or change `CURRENT_SCHEMA`; writes a timestamped text report and a machine-readable JSON snapshot at `artifacts/hr-audit/{SCHEMA}-schema-details-{UTC timestamp}.{txt,json}`. This mode is not a customer-sync approval and must use an approved isolated database connection. Comparing source and target and deciding data/backfill remain separate OPS-03 steps.
- `scripts/compare_hr_schema_snapshots.py --source <source.json> --target <target.json> --output <diff.json>`: offline comparison of two snapshots; reports missing/extra tables and columns, column-definition and identity differences, and structural constraint/index/trigger/static-dependency differences including expressions exposed by Oracle metadata. Constraint/index structural deltas are separated from differences in object names. It also writes a per-column CSV review matrix beside the JSON (or to `--matrix-output <matrix.csv>`), with source/target definitions filled and all data-owner, backfill, approval, validation, and rollback decisions left blank for review. The `backfill_review_candidate` flag only identifies source columns declared NOT NULL without a non-NULL default when absent from the target; it is a schema-level review hint and says nothing about target row counts or actual backfill necessity. It refuses input/output path collisions so a report cannot overwrite either snapshot. The JSON includes both `CapturedAtUtc` values and warns when their skew exceeds configurable `--max-capture-skew-hours` (default 24); this is a freshness review hint, not a migration approval. The tool has no Oracle connection, does not generate DDL, and does not infer backfill or approve data changes. Expressions unavailable or truncated in Oracle's metadata view and dynamic/external dependencies need separate review.
- `--audit-string-lengths`: standalone read-only comparison of every mapped HR string property with an EF max length against Oracle `CHAR_LENGTH`, type, and bytes in `DEV_TEMPLATE`. Reports exact character-length matches, mismatches, missing/non-text columns, unmapped Oracle text columns, and physical HR text tables with no current EF table mapping; writes `artifacts/hr-audit/dev-template-hr-string-lengths.txt`. It does not read personnel values, inspect client schemas, or apply DDL/DML. Summary and compatibility follow-up: `docs/hr/HR_COLUMN_LENGTH_AUDIT_2026-11-12_AR.md`.
- `--widen-currency-code-columns`: standalone, DEV_TEMPLATE-only, idempotent DDL that widens HR `NVARCHAR2 CURRENCY_CODE` columns below 20 characters to 20. Take and verify a Data Pump backup first; values are retained. It refuses to run with any other option and verifies that no narrow HR currency-code column remains. It does not access other schemas or grant permissions.
- `--audit-leave-balance-migration`: runs alone and reads aggregate balance-cycle shape, settings, ledger coverage and dependent workflow counts in a read-only DEV_TEMPLATE transaction. It emits no employee identifiers or individual balances, chooses no migration dates, and changes no data. This is preflight evidence for LEV-16, not a migration or a customer-schema verification.
- `--audit-legacy-payroll`: runs alone and audits aggregate legacy payroll runs, loans, advances, adjustments, handoffs, and receipts in a read-only DEV_TEMPLATE transaction. Verifies that legacy approved runs without handoffs, unfunded loans/advances, and legacy postings without snapshots are identified without guessing or automated data modification. Also counts finalized bank-transfer payroll lines and missing currency/beneficiary snapshots, active loans/advances missing explicit currency codes or referencing zero/multiple ERP currency rows, active-loan schedules with missing, invalid, or unreconciled installments, and schedules whose parent loan row is missing (including pending/partial/skipped rows). Payment audit counts confirmed instructions missing one posted, unreversed PV; failed instructions with a non-voided PV; reversed instructions missing the linked original/reversal vouchers; and prepared instructions with a posted PV. It emits aggregate counts only, no PII or individual amounts, and does not consult current employee profiles. Preflight evidence for ERP-09/INT-13/PAY-20; does not inspect or touch customer schemas.
- `--migration-baseline`: captures a consistent, read-only snapshot of the original HR column names, row counts and SHA-256 fingerprints. Stores no personnel values. Refuses to overwrite an existing `artifacts/hr-audit/hr-migration-baseline.json`; archive it explicitly for a new batch. This manifest is not a backup.
- `--migration-verify`: compares all original HR rows/columns against that baseline. Nonzero exit means changed original data or a failed read. New tables, new columns and constraints still need preflight/schema review. Original balance cycle columns, if already present in the baseline, are included: intentional backfills will be reported as differences for explicit review.
- `--verify-cycle-key`: exercises the real Oracle balance unique key with two distinct cycles in year 9000 and a duplicate cycle. Uses an existing balance only as an employee/type FK source, reserves three negative IDs (refuses collisions), and rolls back every test insert. Confirms that no test rows remain. This mode executes temporary DML and is not read-only.
- `--verify-closed-cycle`: tests the actual repository guard on Oracle inside a rolled-back transaction. Covers a posted header without balance lines, wildcard header, historical overlap after cycle changes, blocked accrual, and open draft/unposted/next cycles. Uses a unique test close in year 9000 and verifies cleanup; does not test concurrent sessions or deploy the application.
- `--install-leave-ledger`: standalone creation of `DEV_TEMPLATE.HR_LEAVE_MOVEMENT`, with unique operation keys, per-balance sequence numbers and single linked reversals, plus restrictive FKs and a DEV_TEMPLATE append-only UPDATE/DELETE trigger (intended ORA-20071). It reports enabled invalid triggers from other owners attached to this table; when present, protection is not accepted and `--verify-leave-ledger` refuses before DML. Take a local Data Pump backup first. Existing rows in other tables are not rewritten; observed openings are created with the first ledger-backed change. Re-runs refresh the trigger and review mappings. Run this explicitly before deploying the ledger code; the broad `--repair` command does not install this table.

Covers opening/grant, usage, carry-forward/expiry, repeated post/unpost, dependent close and reversal, repost, exact linked reversals, running totals, self-service scope and SQL immutability. It records its current phase if Oracle rejects a statement and refuses to run DML if an enabled invalid trigger owned outside DEV_TEMPLATE is attached to `DEV_TEMPLATE.HR_LEAVE_MOVEMENT`. `ORA-04098` during the append-only UPDATE/DELETE assertions is a failed verifier run even when DEV_TEMPLATE trigger metadata reports ENABLED/VALID. Verifies test cleanup. Consumes identity values; does not test concurrent writers.
- `--verify-leave-manual-adjustment`: runs the real leave service/repository against a synthetic leave type inside a rollback-only DEV_TEMPLATE transaction. Checks the Oracle `NUMBER(12,4)` bound, negative correction on a missing balance, persisted adjustment kind/reason and balance effect, protection of pending reservations, linked reversal, exact balance restoration, idempotent retry, changed-reason rejection, and fixture cleanup. Then uses two independent Oracle sessions to prove a duplicate manual operation waits for the employee lock, applies once after the first session rolls back, and leaves no balance/movement after the second rollback; its synthetic leave type is deleted. Consumes identity values and does not alter customer schemas. A successful commit followed by retry is intentionally not exercised because immutable ledger rows cannot be safely removed from the shared schema.

- `--verify-leave-concurrency`: opens independent DEV_TEMPLATE Oracle sessions. First proves the employee `FOR UPDATE` lock blocks a second workflow callback without DML; then seeds a marker leave type and one-day balance and calls the real `LeaveService.SubmitLeaveRequestAsync` concurrently from both sessions with 0.6-day requests. Exactly one PENDING request must be committed while the other observes the reservation and fails for insufficient balance. It races duplicate PENDING cancellation, approval against cancellation for a temporary untracked leave request, and duplicate cancellation of an APPROVED untracked request. Each decision race requires one serialized terminal result and cleanup verification; the approved cancellation also verifies separate actor/date/reason output and creates no balance movement. Approved balance-tracked USAGE reversal still needs an isolated rollback-capable schema because DEV_TEMPLATE has invalid external ledger triggers; this does not cover customer synchronization.
- `--verify-leave-close-concurrency`: uses separate Oracle sessions to prove first-draft serialization and wildcard/type post overlap rejection. A two-session fixture proves the second post waits on the close lock and applies once after the first transaction rolls back. A `SaveChangesInterceptor` injects failure on the repository's second save after its balance/ledger flush, then verifies Oracle rollback and a successful retry; all fixture transactions roll back and draft rows are deleted. It refuses unsuitable/missing balance fixtures, verifies no close/ledger fixture remains, and does not create a payroll run or prove a committed-duplicate post or cashout end-to-end workflow.
- `--verify-payroll-input-lock`: creates temporary payroll periods and a calculated run/line for an existing employee in DEV_TEMPLATE, then exercises the real Oracle payroll lock, employee-date lock, and payroll-input snapshot. Two sessions prove ordered locking of the payroll source/following period set and serialization of the employee/date range. A rollback-only loan/advance fixture proves each repayment schedule and advance balance affects only the targeted period fingerprint.
